바이브코딩은 말로 설명해 만드는 프로그램입니다

Vibe Coding(바이브코딩)은 만들고 싶은 프로그램의 목적과 동작을 사람의 말로 설명하고, AI가 코드를 쓰고 고치고 시험하도록 도와 실제 결과물을 만드는 방식입니다. Vibe는 "떨다"는 뜻의 라틴어 vibrare에서 나온 말로, 진동(vibration)처럼 눈에 보이지 않는 분위기와 느낌을 가리킵니다. 코드 문법부터 외우는 대신, 하고 싶은 일의 느낌과 조건을 대화로 전하는 것이 출발점입니다.

다만 대충 말해도 정확한 프로그램이 나온다는 뜻은 아닙니다. 의도와 조건과 완료 기준을 분명히 말할수록 결과가 좋아집니다. 그리고 AI가 만든 코드가 완전하거나 안전하다는 보장은 없으므로, 결과를 확인하고 승인하는 일은 언제나 사람의 몫입니다. 이 사람을 Owner(오너, 최종 의사결정자)라고 부릅니다. 무엇을 만들지 정하고, 결과를 검수하고, 공개 여부를 승인하는 사람입니다.

처음부터 큰 시스템을 만들 필요는 없습니다. MVP(Minimum Viable Product, 최소 기능 제품)는 핵심 문제 하나를 풀 만큼만 만든 첫 결과물입니다. 작게 만들어 써 보고, 불편한 점을 말로 다시 설명해 고쳐 가는 것이 바이브코딩의 기본 흐름입니다.

이 설명서는 2026년 11월 1일을 기준으로, Claude 유료 플랜(Pro 기준)으로 바이브코딩을 시작하는 분을 위해 꼭 알아야 할 개념과 사용법을 순서대로 안내합니다. 메뉴 이름과 기능은 앱 버전에 따라 달라질 수 있으니 실제 화면을 우선해서 확인해 주십시오.

정리: 말로 설명해 만들고, 확인과 승인은 사람이 합니다.

Claude는 Chat과 Code 두 갈래로 시작합니다

Claude를 바이브코딩에 쓰는 방법은 크게 두 가지입니다. Chat은 대화로 요구사항을 정리하고 코드·문서·파일을 만드는 방식이고, Code는 프로젝트 폴더나 저장소를 직접 읽고 고치고 실행해 보는 개발 전용 방식입니다.

갈래한 문장 설명잘 맞는 일
Chat대화하며 요구사항·코드·문서를 만들고, 파일 생성 같은 여러 단계 작업도 맡긴다아이디어 정리, 자료·문서 제작, 작은 HTML 도구
Code프로젝트 폴더나 저장소에서 파일을 읽고 고치고 실행·검증한다계속 키워 가는 프로그램, 테스트와 버전 관리

여기서 LLM(Large Language Model, 대규모 언어 모델)은 글과 코드를 만들어 내는 "두뇌"에 해당하는 모델입니다. Agent(에이전트, 대리인 代理人)는 라틴어 agere(행하다)에서 온 말로, 목표를 받아 도구를 쓰며 여러 단계를 스스로 수행하는 주체를 뜻합니다. 은행 업무를 대신 처리하는 대리인을 떠올리면 됩니다. 코드를 쓰고 고치고 시험하는 Agent가 Coding Agent(코딩 에이전트)이고, Claude의 Code가 여기에 해당합니다. Tool(도구)은 파일 읽기·쓰기, 명령 실행처럼 Agent가 일하는 데 쓰는 기능으로, Agent의 손과 발이라고 생각하면 됩니다.

Chat 안에서도 Claude가 작업 공간에서 파일을 만들고 여러 단계를 처리할 수 있어서, 별도의 제품을 따로 고르지 않아도 됩니다. 앱 버전에 따라 화면의 탭 이름은 달라질 수 있습니다. 선택의 기준은 하나입니다. 대화로 만들 것인가, 내 프로젝트 폴더와 저장소에서 개발할 것인가.

정리: 대화로 만들면 Chat, 프로젝트를 직접 다루며 개발하면 Code입니다.

Claude는 웹, 데스크톱 앱, 휴대폰으로 만납니다

접속 방법어떻게 시작하나쓸 수 있는 것
웹 브라우저claude.ai에 로그인합니다. 설치가 필요 없습니다.Chat, 그리고 claude.ai/code의 Code(클라우드)
데스크톱 앱Windows 또는 macOS용 앱을 설치하고 같은 계정으로 로그인합니다.한 앱 안에서 Chat과 Code. Linux에는 앱이 없어 명령줄(CLI)을 씁니다.
휴대폰 앱iOS·Android 앱에 로그인합니다.Chat, 그리고 Code 탭에서 클라우드 작업 확인

같은 계정으로 로그인하면 대화·프로젝트·설정이 기기 사이에 이어집니다. 그래서 집에서는 웹, 강의장에서는 데스크톱 앱을 써도 같은 Claude를 만나게 됩니다. 단, 어느 접속 방법을 쓰든 할 수 있는 일이 똑같지는 않습니다. 특히 내 컴퓨터의 폴더를 직접 다루는 일은 데스크톱 앱에서만 가능합니다.

정리: 같은 계정으로 어디서든 접속하지만, 내 폴더를 다루려면 데스크톱 앱이 필요합니다.

접속 방법과 작업 장소는 서로 다른 말입니다

가장 자주 생기는 혼동은 "어디로 접속하는가"와 "일이 어느 컴퓨터에서 실행되는가"를 같은 질문으로 생각하는 것입니다.

질문구분 A구분 B
어디로 접속하는가Web: 브라우저로 접속Desktop: PC 앱을 실행
일이 어느 컴퓨터에서 실행되는가Cloud: Anthropic의 원격 컴퓨터Local: 내 컴퓨터

Cloud(클라우드)는 인터넷 너머에서 빌려 쓰는 컴퓨터 자원이고, Local(로컬)은 내 PC와 내 폴더입니다. 이 둘을 담는 말이 Execution Environment(실행 환경, 實行環境)입니다. environment는 "둘러싸다"는 뜻의 프랑스어 environner에서 왔고, 프로그램을 빙 둘러싸고 있는 컴퓨터가 어디인지를 가리킵니다.

같은 Code 화면이라도 웹 브라우저의 Code와 데스크톱 앱의 Code는 다릅니다. 웹은 클라우드에서만 실행되므로 내 PC 폴더를 고르는 "선택…" 버튼이 없습니다. 데스크톱 앱은 실행 환경을 고를 수 있습니다. 화면에서 이 버튼이 보이는지가 지금 내가 어느 쪽에 있는지를 알려 주는 가장 쉬운 단서입니다.

정리: Web과 Desktop은 접속 방법이고, Cloud와 Local은 일이 실행되는 장소입니다.

생각은 늘 클라우드에서, 일은 장소를 고릅니다

Inference(추론 실행, 推論)은 모델이 입력을 받아 답이나 코드를 만들어 내는 계산 과정입니다. 라틴어 inferre(안으로 끌어오다)에서 온 말로, 주어진 근거에서 결과를 이끌어 낸다는 뜻입니다. Claude는 웹이든 데스크톱 앱이든 Code든, 이 계산을 모두 Anthropic의 클라우드에서 합니다. 데스크톱 앱을 설치해도 모델이 내 PC에서 돌지는 않습니다.

달라지는 것은 "파일을 읽고 쓰고 명령을 실행하는 일"을 어디서 하느냐입니다. 생각하는 곳과 일하는 곳을 따로 보아야 합니다.

모델은 화면에서 고를 수 있습니다. 데스크톱 앱의 Code 입력창 아래에는 모델 이름과 함께 Effort(노력 수준)를 고르는 칸이 있습니다. 예를 들어 "Opus 5.5 / 중간"처럼 보이며, 모델이 얼마나 깊이 생각할지를 정합니다. 높을수록 깊이 생각하지만 시간과 사용량이 더 듭니다. 처음에는 기본값으로 시작하고, 어려운 문제에서만 올려 보십시오.

정리: 생각하는 곳은 항상 클라우드이고, 파일과 명령을 다루는 곳은 환경에 따라 다릅니다.

웹 Chat은 가장 쉬운 출발점입니다

브라우저에서 claude.ai에 로그인해 새 대화를 열면 바로 시작할 수 있습니다. 설치도, 폴더 설정도 필요 없습니다.

할 수 있는 일

  • 대화로 요구사항을 정리하고, 코드와 문서를 만듭니다.
  • Artifact(아티팩트, 산출물)는 대화 중 만든 웹페이지나 문서를 별도의 결과물 화면으로 열어 두는 기능입니다. 만든 HTML 페이지를 바로 열어 보고, 필요하면 공유할 수 있습니다. 처음에는 나만 볼 수 있습니다.
  • Claude의 작업 공간에서 PPT, Excel 같은 파일을 직접 만들어 내려받을 수 있습니다. 내 PC에 Office가 없어도 됩니다.
  • 파일, 이미지, PDF를 올려 읽게 하고, 웹 검색으로 최신 정보를 찾게 할 수 있습니다.
  • Connector(커넥터, 연결 장치)는 Notion, GitHub, Google Drive 같은 외부 서비스를 Claude에 연결하는 기능입니다. 연결 자체에는 추가 요금이 없고, 쓸 때 사용량만 듭니다.
  • 프로젝트의 지침과 자료 파일, 메모리를 함께 활용할 수 있습니다.

한계

  • 내 PC의 폴더를 직접 읽고 쓰지 못합니다. 필요한 파일은 하나씩 올려야 합니다.
  • 만든 결과는 대화와 Artifact 안에 있으므로, 내 PC나 GitHub로 옮기는 단계가 필요합니다.
  • 내 컴퓨터에서 실행해 보거나 Git 이력을 만드는 일은 자동으로 되지 않습니다.

정리: 요구사항 정리, 문서와 작은 HTML 도구 만들기, 개념 학습에 가장 알맞습니다.

요구사항을 네 가지로 말하면 잘 만들어 줍니다

바이브코딩의 결과는 요구사항을 얼마나 분명히 말하느냐에 달려 있습니다. 세 번 이상 반복하는 일 하나를 골라 다음 네 가지를 차례로 적으면 첫 요구사항이 됩니다.

  1. 문제: 지금 어떤 일을 반복하고 있는가?
  2. 현재 방식: 얼마나 자주, 어떤 순서로 하고 있는가?
  3. 원하는 결과: 프로그램이 대신 처리했으면 하는 부분은 무엇인가?
  4. 완료 기준: 결과가 맞는지 무엇으로 확인할 것인가?

예를 들어 한글 타자 연습 웹앱은 다음과 같이 요청할 수 있습니다.

브라우저에서 실행하는 한글 타자 연습 프로그램을 만들어 주세요. 선택한 글쇠를 20회 입력하게 하고, 정답과 오답을 표시하며, 정확도를 계산해 주세요. 진행 결과를 확인할 수 있어야 합니다. 프로그램을 열고 실행하는 방법도 알려 주세요.

결과가 마음에 들지 않을 때는 "마음에 안 들어"라고 말하기보다 기대한 동작과 실제 동작의 차이를 말하십시오. 예를 들어 "키를 한 번 누르면 한 글자가 입력되어야 하는데, 지금은 두 번 입력됩니다. 원인을 찾아 고치고 시험해 주세요."처럼 말하면 Claude가 정확히 고칠 수 있습니다. 처음부터 모든 기능을 요구하지 말고, 꼭 필요한 기능 세 가지와 이번에는 하지 않을 일을 함께 말하면 MVP가 작고 단단하게 만들어집니다.

정리: 문제, 현재 방식, 원하는 결과, 완료 기준을 말하고, 고칠 때는 기대와 실제의 차이를 말합니다.

만든 결과물은 네 단계를 거쳐 내 것이 됩니다

"AI가 만들었다"와 "내가 쓸 수 있다" 사이에는 네 단계가 있습니다.

단계하는 일
1. 생성요구사항으로 코드와 파일을 만듭니다.
2. 확보결과 파일과 변경 이력을 내가 통제할 수 있는 곳(내 PC나 GitHub)에 보관합니다.
3. 검증실제로 실행해 요구사항을 충족하는지 확인합니다.
4. 배포필요하면 다른 사람도 쓸 수 있게 공개합니다.

이 가운데 하나라도 빠지면 만들었어도 쓰기 어렵습니다. 대화 속에 코드가 보인다고 해서 내 폴더에 파일이 생긴 것은 아니고, 파일이 생겼다고 해서 웹사이트가 공개된 것도 아닙니다. 이 설명서의 뒷부분은 각 방식에서 결과물이 처음 어디에 생기고, 어떻게 내 것으로 확보하는지를 하나씩 안내합니다.

정리: 생성, 확보, 검증, 배포를 모두 거쳐야 쓸 수 있는 프로그램이 됩니다.

Git과 GitHub는 코드의 이력과 보관 장소입니다

Git(깃)은 코드와 문서의 변경 이력을 기록하고 버전을 관리하는 도구이고, GitHub(깃허브)는 Git으로 관리하는 프로젝트를 인터넷에 보관하고 함께 작업하는 서비스입니다. Git은 원고의 수정 이력이고, GitHub는 그 원고를 여러 사람이 공유하고 검토하는 온라인 작업실이라고 생각하면 쉽습니다.

프로젝트를 담아 두는 공간을 Repository(저장소, 貯藏所)라고 합니다. 라틴어 reponere(다시 두다)에서 온 말로, 물건을 모아 두는 창고입니다. 웹 Code는 이 저장소를 출발점으로 삼습니다.

용어뜻
Branch(브랜치)기존 작업 흐름과 분리해 새 작업을 하는 갈래입니다.
Commit(커밋)이번 변경을 하나의 이력으로 기록합니다. 라틴어 committere(맡기다)에서 온 말로, 변경을 이력에 맡겨 두는 것입니다.
Push(푸시)내 컴퓨터의 기록을 원격 저장소에 올립니다.
Pull(풀)원격 저장소의 변경을 내 컴퓨터로 가져옵니다.
Pull Request(PR, 변경 병합 요청)내 Branch의 변경을 다른 Branch에 합쳐 달라고 제안하고 검토받는 절차입니다.
Merge(머지, 병합)검토가 끝난 변경을 실제로 합칩니다. PR은 제안이고 Merge는 실행입니다.

흐름은 이렇습니다. Branch를 만들어 작업하고, Commit과 Push로 올린 뒤, PR로 검토를 받고 Merge합니다. 혼자 만드는 프로젝트에서도 이 흐름이 안전장치가 됩니다. 마음에 들지 않으면 Merge하지 않고 버리면 되기 때문입니다.

정리: Git은 이력을, GitHub는 보관과 협업을 맡고, PR로 검토한 뒤 Merge합니다.

웹 Code는 GitHub 저장소를 클라우드에서 고칩니다

웹 Code는 브라우저의 claude.ai/code에서 시작합니다. 저장소를 선택하고 작업을 입력하면, Claude가 그 저장소를 Anthropic이 관리하는 가상 컴퓨터(VM)에 새로 복제해 코드를 고치고 명령을 실행해 본 뒤, 변경을 Branch로 올려 줍니다. 사용자는 변경 내용을 검토하고 PR로 병합합니다.

특징

  • 앱을 닫거나 자리를 비워도 작업이 계속됩니다. 노트북에서 시작한 작업을 휴대폰에서 확인할 수도 있습니다.
  • 웹 Code는 GitHub 저장소만 읽습니다. 클라우드에서 돌기 때문에 내 PC 폴더에는 접근하지 못합니다.
  • 세션은 저장소를 새로 복제해 시작하므로, 커밋하지 않은 내용은 클라우드에 없습니다. 중요한 결과는 반드시 Git에 남깁니다.
  • 권한 모드는 Accept edits, Plan, Auto 가운데 고릅니다. 클라우드 환경은 이미 격리되어 있어 모든 권한을 풀어 두는 Bypass permissions 모드는 제공되지 않습니다.
  • 네트워크 접근 범위와 작업 시작 때 실행할 설정은 환경 설정에서 정합니다.
  • 클라우드 작업도 다른 Claude 사용량과 같은 한도를 씁니다. 여러 작업을 동시에 돌리면 한도가 빨리 줄어듭니다.

잘 맞는 일과 한계

이미 GitHub에 올라 있는 프로젝트의 버그 수정이나 반복적인 작업을 맡겨 두고 자리를 비울 때 알맞습니다. 반면 GitHub가 출발점이므로, GitHub에 올리지 않은 내 PC의 프로젝트는 바로 다룰 수 없습니다.

정리: 저장소를 클라우드에서 고치고 PR로 돌려주며, 내 PC 폴더는 볼 수 없습니다.

웹 Code는 이 순서로 시작합니다

  1. GitHub에 빈 저장소 만들기. 새 프로젝트라면 GitHub 사이트에서 먼저 빈 저장소를 만듭니다. 저희 실험에서는 Claude가 저장소를 읽고 쓰는 것은 되었지만, 계정에 새 저장소를 만들거나 전체 저장소 목록을 보는 것은 되지 않았습니다.
  2. 로그인. 브라우저에서 claude.ai/code에 접속해 Claude 계정으로 로그인합니다.
  3. GitHub 연결. 안내에 따라 Claude GitHub 앱을 설치하고 접근할 저장소를 허용합니다.
  4. 환경 만들기. 처음에 클라우드 환경을 하나 만듭니다. 이 환경이 작업 중 네트워크를 어디까지 쓸지, 작업 시작 때 무엇을 실행할지를 정합니다.
  5. 저장소와 Branch 고르기. 입력창 아래의 저장소 선택에서 대상을 고릅니다.
  6. 권한 모드 고르기. 처음에는 Plan을 권합니다. Claude가 접근 방법을 먼저 제안하고, 승인한 뒤에야 파일을 고칩니다.
  7. 작업 입력. 요구사항을 네 가지로 정리해 입력합니다.
  8. 검토. 끝나면 변경 내용(Diff)을 읽고, 이상이 없을 때만 PR을 병합합니다.
  9. 내 PC로 가져오기. 병합한 결과를 내 컴퓨터에서 Pull해 실행해 봅니다.

정리: 빈 저장소, 로그인, GitHub 연결, 환경, 작업 입력, Diff 검토, Pull 순서입니다.

데스크톱 앱은 설치하고 화면 구성부터 읽습니다

Claude 데스크톱 앱은 Windows와 macOS에서 설치해 쓰며, 한 앱 안에 Chat과 Code를 함께 담고 있습니다. Windows에서 Code를 처음 열 때는 Git for Windows가 설치되어 있어야 하며, 설치한 뒤에는 앱을 다시 시작합니다.

Code 화면은 다음 요소로 읽으면 됩니다.

위치이름하는 일
왼쪽 위모드 전환 버튼말풍선은 Chat, </> 모양은 Code로 바꿉니다.
왼쪽 사이드바새로 만들기, 검색, 아티팩트, 사용자 지정새 세션 시작, 지난 세션 검색, 만든 결과물 모음, 기능 확장 설정
입력창 아래, 왼쪽이 컴퓨터작업이 실행되는 곳입니다. 바꾸면 클라우드 등을 고를 수 있습니다.
입력창 아래, 가운데선택…작업할 폴더를 고릅니다. Claude는 이 폴더 안만 보고 일합니다.
입력창 아래권한 모드파일 수정과 명령 실행을 매번 물을지 정합니다.
입력창 아래, 오른쪽모델과 Effort쓸 모델과 생각의 깊이를 정합니다.
오른쪽 위터미널 등명령창과 실행 화면 미리보기를 엽니다.

Session(세션)은 Code 안의 대화 하나입니다. 라틴어 sessio(앉음)에서 온 말로, 한자리에 앉아 이어 가는 하나의 작업 시간이라는 뜻입니다. 세션마다 자기 대화 기록, 프로젝트 폴더, 코드 변경을 따로 가지며, 여러 세션을 나란히 열어 둘 수 있습니다.

정리: 입력창 아래 줄의 "이 컴퓨터, 선택…, 권한 모드, 모델"이 가장 중요한 네 칸입니다.

데스크톱 Chat은 내 폴더를 연결해 일합니다

데스크톱 앱의 Chat 대화를 내 컴퓨터의 폴더와 연결하면, 파일을 하나씩 올리지 않아도 Claude가 폴더의 파일을 읽고 결과를 돌려놓을 수 있습니다. 저희가 직접 확인한 구조는 다음과 같습니다.

  1. Claude가 필요한 파일 몇 개만 골라 내 컴퓨터에서 클라우드 작업 공간으로 복사합니다. 폴더 전체가 올라가지는 않았습니다.
  2. 처리는 클라우드 작업 공간에서 이루어집니다. 파이썬 도구 실행이나 가상 브라우저로 화면을 확인하는 일도 이곳에서 일어납니다.
  3. 결과물이 있으면 내 폴더로 복사해 저장합니다.

Sandbox(샌드박스, 모래상자)는 아이들이 모래상자 안에서 마음껏 놀아도 바깥이 어질러지지 않듯, 안에서 무엇을 실행해도 바깥에 영향을 주지 않는 격리된 실행 공간입니다. 이 작업 공간은 내 컴퓨터가 아니라 클라우드에 있고, 한동안 쓰지 않으면 회수되어 사라집니다.

내 컴퓨터에서 명령을 직접 실행하는 연결이 따로 켜져 있으면 그 명령은 내 컴퓨터에서 실행됩니다. 이런 연결이 없으면 폴더 연결은 파일을 옮기는 통로 역할입니다. 연결 상태는 대화마다 다를 수 있으니, 작업을 시킨 그 대화창에 "지금 이 작업을 실행하는 컴퓨터의 운영체제와 작업 폴더 경로를 알려줘"라고 물어 직접 확인해 보십시오. 리눅스 경로가 나오면 클라우드, 윈도우 경로가 나오면 내 컴퓨터입니다.

주의할 점. 파일이 클라우드로 복사될 수 있으므로, 비밀번호와 API Key가 든 .env 같은 파일은 연결한 폴더에 두지 않습니다.

정리: 폴더 연결은 필요한 파일을 복사해 클라우드에서 처리하고 결과를 돌려놓습니다. 비밀 파일은 두지 않습니다.

데스크톱 Code는 실행 환경을 고릅니다

데스크톱 앱의 Code는 로컬 전용이 아닙니다. 일이 실행될 곳을 세 가지 가운데 고를 수 있습니다.

환경코드가 실행되는 곳특징
Local (이 컴퓨터)내 컴퓨터내 폴더를 직접 읽고 씁니다. GitHub 없이도 시작할 수 있습니다. 컴퓨터가 켜져 있고 앱이 열려 있어야 합니다.
RemoteAnthropic 클라우드앱을 닫아도 계속 진행됩니다. 웹 Code와 같은 방식이며 GitHub 저장소가 필요합니다.
SSH내가 관리하는 다른 컴퓨터원격 서버나 다른 PC에서 작업합니다.

휴대폰에서 지시를 보내는 연결도 있습니다. Remote Control은 휴대폰에서 내 컴퓨터의 Claude Code로 작업을 보내는 기능이고, Dispatch는 휴대폰에서 데스크톱 앱으로 작업을 넘기는 기능입니다. 처음에는 Local과 Remote의 차이만 정확히 이해하면 충분합니다.

Local Code에서 할 수 있는 일. 고른 폴더의 파일을 직접 읽고 수정하고, 터미널에서 테스트를 실행하며, 바뀐 부분을 비교해(Diff) 댓글을 달고, PR을 만든 뒤 자동 검사 상태를 확인합니다. 내장 미리보기로 개발 서버를 띄워 실행 화면을 확인하고, 여러 세션을 동시에 돌릴 수 있습니다.

정리: 내 폴더를 직접 다루려면 Local, 앱을 닫고도 맡기려면 Remote를 고릅니다.

Local Code는 이 순서로 첫 작업을 맡깁니다

  1. Code로 전환. 데스크톱 앱 왼쪽 위에서 </> 모양 버튼을 누릅니다.
  2. 실행 위치 확인. 입력창 아래 왼쪽이 "이 컴퓨터"인지 확인합니다.
  3. 폴더 선택. 가운데 "선택…"을 눌러 작업할 폴더를 고릅니다. 고르면 그 자리에 폴더 이름이 표시됩니다.
  4. 권한 모드를 Manual로. 처음에는 Claude가 하는 일을 직접 보고 승인하는 Manual로 시작합니다.
  5. 요구사항 입력. 네 가지 요구사항으로 작업을 설명합니다. 처음에는 "바로 고치지 말고 계획부터 보고해 줘"라고 요청하는 것이 안전합니다.
  6. 계획과 변경 확인. Claude가 파일을 고치기 전에 보여 주는 내용을 읽고 승인합니다.
  7. 실행해 보기. 미리보기나 터미널로 실제 동작을 확인합니다.
  8. Git에 남기기. 이미 Git과 GitHub 로그인이 되어 있다면 그 설정을 그대로 씁니다. 새 저장소를 만들려면 Git만으로는 부족하고 GitHub CLI(gh)가 필요하며, 터미널에서 gh auth status로 로그인 상태를 확인합니다.

git push처럼 바깥에 영향을 주는 명령은 "이번만 허용"으로 두고 매번 승인하십시오. 읽기만 하는 git status 같은 명령은 항상 허용해도 안전합니다.

정리: 폴더를 고르고, Manual로 시작하며, push는 매번 승인합니다.

권한 모드는 Claude의 손을 묶는 안전장치입니다

Permission mode(권한 모드, 權限)는 Claude가 파일을 고치거나 명령을 실행할 때 사용자에게 얼마나 자주 물을지를 정하는 설정입니다. 권한(權限)은 어떤 일을 해도 좋다고 허락한 범위라는 뜻입니다.

모드Claude의 행동어울리는 때
Manual파일 수정과 명령 실행을 매번 물어봅니다.처음 배울 때, 중요한 프로젝트
Accept edits파일 수정은 알아서 하고, 그 밖의 위험한 일은 묻습니다.익숙해진 뒤 반복 작업
Plan먼저 계획을 제안하고, 승인해야 고칩니다.큰 변경, 접근 방법을 먼저 보고 싶을 때
Auto가능한 일을 알아서 진행합니다.충분히 신뢰하는 작업

클라우드 세션에서는 Accept edits, Plan, Auto를 고릅니다. 클라우드 환경은 이미 격리되어 있어 파일 수정은 미리 허용되어 있습니다. 처음에는 Manual로 Claude가 무엇을 하는지 눈으로 보고, 익숙해지면 Accept edits나 Plan으로 옮기는 순서를 권합니다. 기본 규칙은 하나입니다. 되돌리기 어려운 일일수록 더 엄격한 모드에서 하십시오.

정리: Manual로 시작해, 익숙해지면 Accept edits나 Plan으로 옮깁니다.

일의 성격에 따라 알맞은 방식이 다릅니다

하려는 일알맞은 방식이유
아이디어를 정리하고 요구사항을 만든다웹 Chat설치 없이 바로 시작하고 대화에 집중할 수 있습니다.
문서, 슬라이드, 작은 HTML 도구를 만든다웹 Chat 또는 데스크톱 ChatArtifact와 파일 생성 기능을 씁니다.
내 PC 폴더의 자료를 읽고 정리한다데스크톱 Chat (폴더 연결)파일을 하나씩 올릴 필요가 없습니다.
GitHub의 프로젝트를 맡겨 두고 자리를 비운다웹 Code 또는 데스크톱 Code의 Remote앱을 닫아도 클라우드에서 계속됩니다.
내 PC의 프로젝트를 개발하고 시험한다데스크톱 Code의 Local내 폴더, 터미널, 테스트, Git을 한 흐름에서 씁니다.
여러 Agent가 역할을 나눠 협업한다IDE에 확장과 CLI를 연결역할별로 Agent를 나누고 공통 문서로 협업시킬 수 있습니다.

정리: 대화는 Chat, 폴더 연결은 데스크톱 Chat, 개발은 Code, 협업은 IDE입니다.

대화와 작업은 어디까지 이어지는가

항목이어지는 범위
Chat 대화 기록같은 계정이면 웹, 데스크톱, 휴대폰에서 이어서 볼 수 있습니다.
프로젝트, 설정, 선호계정에 저장되어 어디서나 같습니다.
Connector계정 단위로 연결되어 웹, 데스크톱, Code에서 함께 씁니다.
클라우드 Code 세션웹, 휴대폰, 데스크톱에서 이어서 볼 수 있습니다.
Local 작업과 Local 세션내 컴퓨터가 중심입니다. 다른 기기에서 이어 보는 방식과 기록이 남는 위치는 환경마다 다르게 안내되므로, 실제 화면으로 확인합니다.
Desktop Extensions설치한 기기에서만 쓸 수 있습니다.
사용량 한도웹, 데스크톱, 휴대폰, Code가 하나로 합산됩니다.

대화가 이어지는 것과 새 대화가 앞 대화의 내용을 자동으로 아는 것은 다릅니다. 프로젝트 안의 대화는 같은 프로젝트의 지난 대화를 검색해 참고할 수 있지만, 프로젝트 경계를 넘는 범위는 제한됩니다. 계정을 바꾸면 이전 세션 기록이 보이지 않는다는 보고도 있으므로, 중요한 결과는 반드시 GitHub 같은 내가 통제하는 곳에 따로 남기십시오.

맥락을 잇는 가장 확실한 방법은 대화창이 기억하게 하지 않고 기록이 기억하게 하는 것입니다. 확정한 요구사항과 현재 상태를 문서로 적어 저장소나 Notion에 두고, 새 대화를 열 때마다 그 문서를 읽게 하십시오.

정리: Chat은 계정으로 이어지고, Local 작업은 환경별로 확인하며, 맥락은 기록 문서로 잇습니다.

사용량은 한 곳에 합산됩니다

유료 플랜은 무제한이 아니라 두 겹의 한도 안에서 씁니다. 하나는 5시간마다 초기화되는 세션 한도이고, 다른 하나는 매주 초기화되는 주간 한도입니다. 웹, 데스크톱, 휴대폰, Code에서 쓴 양이 모두 같은 한도에 더해집니다. 창을 여러 개 열어도, 기기를 여러 대 써도 문제는 없지만 한도는 하나입니다. 설정의 사용량 화면에서 지금 얼마나 썼는지, 언제 초기화되는지, 제품별 비중이 어떤지를 볼 수 있습니다.

한도에 닿으면 초기화 시각까지 기다리거나, 사용량 크레딧을 사서 계속하거나, 플랜을 올릴 수 있습니다. Code 작업은 한도에 닿으면 그 자리에서 멈추므로, 작업을 작게 나누고 단계마다 저장해 두면 초기화 뒤 이어서 할 수 있습니다.

사용량을 많이 쓰는 순서

  1. 아주 긴 대화. 답을 낼 때마다 대화 전체를 다시 읽기 때문에 길수록 많이 듭니다.
  2. 파일과 웹페이지를 만드는 작업, 이미지 처리, 저장소 내려받기 같은 작업형 일
  3. 큰 화면 전체 캡처
  4. 이미 보낸 자료를 다시 보내는 일
  5. 높은 성능 모델과 깊은 사고 설정

아끼는 방법

  • 주제가 바뀌면 새 대화를 열고, 맥락은 기록 문서로 잇습니다.
  • 화면 캡처는 필요한 부분만 잘라서 보냅니다.
  • 같은 대화에서는 "앞의 결과에서 이것만 바꿔 줘"라고 말합니다.
  • 큰 결과물은 내용을 확정한 뒤 한 번에 만들게 합니다.
  • 사용량 화면을 수시로 봅니다.

정리: 한도는 하나로 합산되며, 긴 대화와 큰 작업이 가장 많이 씁니다.

결과물이 남는 곳과 가져오는 길을 구분합니다

만든 곳결과물이 처음 있는 곳내 것으로 가져오는 길
웹 Chat대화, Artifact, 클라우드 작업 공간파일 내려받기, 코드 복사, Artifact 공유, 이후 내 PC나 GitHub에 보관
웹 CodeGitHub의 Branch와 PRPR 병합 후 내 PC에서 Pull
데스크톱 Chat (폴더 연결)연결한 내 폴더이미 내 폴더에 있습니다.
데스크톱 Code, Local선택한 내 폴더이미 내 폴더에 있습니다. Commit과 Push로 GitHub에 올립니다.
데스크톱 Code, RemoteGitHub의 Branch와 PRPull로 가져오거나 세션을 로컬로 이어받습니다.
Notion, Drive 등 Connector해당 서비스그 서비스에서 편집하고 보관합니다.

결과물이 머무는 곳은 세 군데로 나누어 생각하십시오. 첫째, Claude 안의 대화와 프로젝트와 Artifact. 둘째, 내 PC의 폴더. 셋째, GitHub 저장소. 모든 결과물을 GitHub에 올릴 필요는 없지만, 오래 고쳐 쓸 프로젝트는 GitHub를 기준 원본으로 삼고, 지우기 전에는 목록과 안전성을 점검한 뒤 백업과 동기화를 확인합니다.

GitHub에 올린다고 웹사이트가 자동으로 공개되지는 않습니다. 저장소는 소스를 보관하는 곳이고, Deployment(배포, 配布)는 다른 사람이 실제로 쓰도록 제공하는 별개의 절차입니다. HTML, CSS, JavaScript만으로 동작하는 정적 웹앱은 GitHub Pages로 공개할 수 있습니다. 서버나 데이터베이스, 비밀 키가 필요한 프로그램은 다른 실행 환경이 필요합니다.

정리: 어디서 만들었는지에 따라 처음 있는 곳이 다르므로, 내 통제 아래의 장소에 확보합니다.

공개하기 전에는 점검표로 확인합니다

GitHub에 올리기, 배포하기, 남에게 제출하기처럼 바깥에 공개되는 일은 되돌리기 어렵습니다. 실행하기 직전에 다음을 확인하고, 마지막 승인은 Owner가 합니다.

  • Git 저장소의 최상위 폴더(root)가 공개하려는 폴더가 맞는가?
  • 공개될 파일의 전체 목록을 직접 보았는가?
  • .env, API Key, 토큰, 결제 정보, 개인정보, Agent와 나눈 대화 기록과 로그, 관계없는 원본 자료가 빠져 있는가?
  • README에 목적, 사용 방법, 실행 조건이 적혀 있는가?
  • 테스트와 실제 화면 확인을 마쳤는가?
  • 배포했다면 주소가 올바르게 작동하는가?
  • 최종 승인권자가 승인했는가?

Claude에게도 "push하기 전에 공개될 파일 목록과 제외 대상을 보여 주고 승인을 받아 줘"라고 요청해 두면 좋습니다. 연결한 폴더의 파일이 클라우드로 복사될 수 있다는 점도 기억하고, 비밀 정보가 든 파일은 처음부터 작업 폴더 밖에 두십시오.

정리: 공개 직전에는 목록과 제외 대상을 눈으로 확인하고 직접 승인합니다.

같은 결과가 필요하면 프로그램을 저장합니다

같은 요청을 Claude에게 다시 하면 결과는 매번 조금씩 달라집니다. 저희가 같은 변환 작업을 두 가지 방식으로 시켜 보았을 때도, 본문은 같았지만 결과 파일의 길이는 약 3만 자와 약 4만 자로 서로 달랐습니다. 모델은 확률적으로 글과 코드를 만들기 때문입니다.

Deterministic(결정적, 決定的)은 같은 입력을 넣으면 언제나 같은 출력이 나오는 성질입니다. 프로그램은 결정적이고, LLM은 그렇지 않습니다. 그래서 같은 결과를 반복해서, 그리고 빠르게 얻고 싶다면 Claude에게 매번 새로 만들라고 하지 말고, 변환 작업을 해 주는 프로그램(예: build.py)을 폴더에 저장해 두고 그 프로그램을 직접 실행하면 됩니다. 모델을 거치지 않으므로 시간도 크게 줄어듭니다.

이렇게 요청하면 됩니다.

이 변환을 반복할 수 있게 변환 프로그램을 이 폴더에 저장하고, 실행해서 결과 파일을 다시 만들어 주세요.

주의할 점이 있습니다. 저장한 프로그램은 첫 결과의 장점과 단점을 그대로 복제합니다. 그러므로 첫 결과를 충분히 검수한 뒤에 저장하십시오. 이것은 "대화창이 기억하게 하지 말고 기록이 기억하게 하자"는 원칙과 같습니다. 프로그램이 폴더에 남으면 폴더가 기억합니다.

정리: 반복해서 같은 결과가 필요하면 프로그램을 저장하고 직접 실행합니다.

채팅에서 IDE로 옮길 때를 알려 주는 네 신호

IDE(Integrated Development Environment, 통합 개발 환경)는 파일을 보고, 고치고, 실행하고, 시험하는 일을 한 화면에서 하는 개발 프로그램입니다. 채팅만으로도 많은 것을 만들 수 있지만, 다음 네 가지가 보이면 IDE로 옮길 때입니다.

  1. 오래 쓰고 계속 키울 때. 결과물이나 만드는 방법이 오래 쓰이고 계속 업그레이드됩니다.
  2. 작은 수정에도 전체가 흔들릴 때. 한 곳을 고쳤는데 다른 곳이 깨집니다.
  3. 숨겨야 할 키가 있거나 내 컴퓨터 자원에 기댈 때. 비밀 키를 감춰야 하거나 내 컴퓨터의 자원에 의존합니다.
  4. 실행해 보고 고치는 반복이 많을 때. 돌려 보고 오류를 고치는 왕복이 잦습니다.

이 네 신호는 "채팅은 나쁘고 IDE는 좋다"는 뜻이 아닙니다. 짧게 쓰고 끝나는 도구는 채팅으로 충분합니다. 신호가 하나라도 뚜렷해지면 그때 Code와 IDE로 옮겨 가면 됩니다.

정리: 오래 키울 때, 흔들릴 때, 비밀 키가 있을 때, 반복해서 고칠 때 IDE로 옮깁니다.

만드는 쪽과 검사하는 쪽을 나눕니다

한 AI가 계획도 세우고 코드도 쓰고 검사까지 하면, 자기가 만든 것을 자기가 확인하는 셈이라 놓치는 부분이 생깁니다. 그래서 역할을 나눕니다.

  • Vibe Agent(바이브 에이전트)는 사용자의 생각을 질문으로 구체화해 요구사항을 만들고, 기획서와 결과물을 요구사항에 비추어 검토하는 역할입니다. Claude의 Chat이 맡을 수 있으며, 공식 제품명이 아니라 이 설명서에서 쓰는 역할 이름입니다.
  • Coding Agent는 합의된 요구사항을 바탕으로 구현하고 테스트하는 역할입니다. Claude Code가 맡을 수 있습니다.
  • Owner는 문제와 우선순위를 정하고, 최종 검수와 공개 승인을 합니다.

책임을 AI에게 모두 넘기지 않습니다. 코드를 누가 쓰느냐보다 최종 의도와 승인권을 누가 갖느냐가 중요합니다. 요구사항 문서에 적히지 않은 것은 AI도 판단할 수 없으므로, 판단이 애매하면 추측하지 말고 Owner에게 묻게 하십시오.

기록 문서로 약속하기

역할을 나눈 뒤에는 같은 채팅창에 내용을 계속 복사하는 대신, 확정한 문서를 저장소에 두고 모든 Agent가 읽게 합니다. 예를 들어 OWNER_REQUIREMENTS.md에는 확정한 요구사항과 검수 기준을, STATE.md에는 현재 진행 상태를, DECISIONS.md에는 중요한 결정과 이유를 적습니다. 이 파일 이름은 예시이며 서비스가 요구하는 고정 이름은 아닙니다.

진행 순서는 요구사항 합의, Coding Agent의 기획, Vibe Agent의 검토, 구현, 테스트와 독립 검토, Owner 확인, 공개 승인입니다. 같은 모델 계열이라 규칙과 지식은 문서로 옮길 수 있지만, 자동으로 쌓이는 메모리나 "만드는 쪽과 검사하는 쪽을 물리적으로 나눈다"는 구조는 옮겨지지 않으므로 한 Agent의 지침 파일에 모든 역할을 몰아 넣지 마십시오.

정리: 만드는 Agent와 검사하는 Agent를 나누고, 약속은 기록 문서로 남기며, 승인은 Owner가 합니다.

여러 Agent는 IDE에서 역할을 나눠 일합니다

IDE 안에서는 기본 Agent, 확장 프로그램, 터미널의 명령줄 도구가 한 프로젝트 폴더를 함께 다룰 수 있습니다. Extension(확장 프로그램, 擴張)은 IDE에 새 기능을 덧붙이는 구성 요소이고, CLI(Command-Line Interface, 명령줄 인터페이스)는 글자로 명령을 입력해 프로그램을 제어하는 방식입니다. Terminal(터미널)은 CLI를 실행하는 명령창으로, 라틴어 terminus(끝, 경계)에서 온 말입니다. 사용자가 명령을 입력하는 맨 끝자리라는 뜻입니다.

구성예시맡을 수 있는 일
IDE 기본 AgentAntigravity IDE의 기본 Agent구현 조율, 일반 작업 지원
IDE 확장Claude Code 확장, Codex 확장기획, 코드 작성, 검토

Claude Code의 IDE 확장과 CLI는 같은 Claude Code의 다른 접근 방법이어서 설정과 대화 기록을 함께 씁니다. 데스크톱 앱 속 Code와 명령줄로 설치한 Claude Code도 같은 Claude Code입니다. CLI 설치 여부는 터미널에서 claude --version을 입력해 버전 번호가 나오는지로 확인합니다. 데스크톱 앱에서 CLI 대화를 이어받을 때는 /desktop 명령을 씁니다.

서비스마다 구독과 과금은 따로입니다. Claude Code는 Claude 유료 플랜에서 쓰고 사용량도 같은 한도에 합산되며, OpenAI의 Codex와 ChatGPT 구독은 별개입니다. 여러 Agent를 설치한다고 자동으로 협업하지도 않습니다. 각 Agent에게 역할을 정해 주고, 공통 요구사항 문서와 변경 이력, 완료 보고 양식을 공유하고, 같은 파일을 동시에 고치지 않도록 작업 범위를 나누어야 합니다.

계획을 맡은 Agent와 구현을 맡은 Agent는 서로의 대화를 이어받지 않고 새 세션으로 시작하게 하십시오. 그래야 기획자와 구현자의 역할이 뒤섞이지 않습니다. 또한 Claude Code와 Codex는 프로젝트 최상위 폴더의 지침 파일(AGENTS.md 등)은 자동으로 읽지만, 하위 폴더 안의 파일까지 저절로 읽는다고 기대하지 말고 최상위 폴더에 연결 지침을 두십시오.

정리: 확장과 CLI에 역할을 나눠 주고, 공통 문서와 새 세션 규칙으로 협업시킵니다.

전산화, 자동화, Agent화 순서로 키웁니다

반복되는 일을 단계적으로 맡기는 길은 세 단계입니다. Computerization(전산화, 電算化)는 종이나 손으로 하던 정보를 컴퓨터에서 다룰 수 있게 만드는 단계입니다. Automation(자동화, 自動化)는 정해진 규칙과 순서에 따라 반복 작업을 저절로 실행하는 단계입니다. Agent화(Agentization)는 목표와 상황에 따라 AI Agent가 판단하고 도구를 쓰고 검토를 요청하도록 구성하는 단계로, 단계를 이해하기 위해 쓰는 설명용 표현입니다.

개인 영상 기록촬영 장소·날짜·파일명 기록폴더 생성과 정보 수집 자동화소개글 초안과 반영 제안을 만들고 승인 요청

어느 단계에서든 외부에 게시하거나 발송하거나 구매하는 일처럼 중요한 동작은 사용자 확인 절차를 둡니다. Agent는 사람의 판단을 대신하는 존재가 아니라 반복 작업을 맡아 사람이 더 중요한 일에 집중하도록 돕는 수행 체계입니다.

나의 첫 문제 정의서

시작은 항목 몇 줄을 채우는 것입니다. 다음 항목을 한 줄씩 적어 Claude에게 보여 주면 첫 MVP의 요구사항이 됩니다.

  • 내가 반복하는 일
  • 지금 이 일을 하는 방법
  • 불편한 점과 반복 횟수
  • 최종적으로 원하는 결과
  • 첫 MVP에 꼭 필요한 기능 세 가지
  • 이번 MVP에서는 하지 않을 일
  • 결과가 제대로 됐다고 판단하는 기준
  • 저장할 위치(내 PC, 클라우드, GitHub)
  • 배포 대상(나만, 동료, 전체 공개)
  • 최종 승인자

정리: 먼저 컴퓨터에 옮기고, 규칙을 자동화하고, 판단이 필요한 일을 Agent에게 맡깁니다.

모르면 추측하지 말고 직접 물어서 확인합니다

Claude의 기능과 화면은 자주 바뀌므로, 안내서의 설명과 내 화면이 다를 수 있습니다. 그럴 때는 추측하지 말고 확인하는 습관이 가장 믿을 만합니다.

실행 위치 확인 질문

작업을 시킨 바로 그 대화창에 다음처럼 물어보십시오.

지금 이 작업을 실행하는 컴퓨터의 운영체제와 현재 작업 폴더 경로를 알려줘

/home/…처럼 리눅스 경로가 나오면 클라우드에서 실행 중이고, C:\… 같은 윈도우 경로가 나오면 내 컴퓨터에서 실행 중입니다. 이 질문은 반드시 작업한 그 대화창에 해야 합니다. 다른 대화창의 Claude는 그 창의 진행 과정을 볼 수 없고 결과 파일만 볼 수 있기 때문입니다.

파일을 줄지, 화면 캡처를 줄지

알고 싶은 것더 정확한 방법
글자, 숫자, 코드가 원본과 같은가파일 (그림 속 글자는 잘못 읽을 수 있습니다)
HTML이 어떻게 보이고 작동하는가파일을 Claude가 직접 열어 확인
내 컴퓨터와 브라우저에서 실제로 어떻게 보이는가화면 캡처
오류 메시지, 대화창 진행 과정, 설정 화면, 버튼 위치화면 캡처

캡처에 긴 글자가 많을 때는 같은 내용을 복사해 글자로 붙여 주는 편이 더 정확합니다.

시간과 사용량은 직접 재서 비교

작업에 걸린 시간과 사용량은 Claude가 정확히 알 수 없습니다. 같은 작업을 서너 번 반복해 시작과 끝 시각을 적고, 작업 전후의 사용량 화면 수치를 비교하면 가장 정확합니다.

정리: 모르면 그 대화창에 물어 확인하고, 시간과 사용량은 직접 재어 봅니다.

자주 헷갈리는 질문 여덟 가지

웹 Code로 내 PC 폴더를 작업할 수 있나요?
할 수 없습니다. 웹은 클라우드에서 실행되어 내 PC 폴더를 볼 수 없습니다. GitHub 저장소를 쓰거나 데스크톱 앱의 Code를 쓰십시오.
데스크톱 앱을 설치하면 AI 모델이 내 PC에서 돌아가나요?
아닙니다. 모델은 클라우드에서 실행됩니다. 내 컴퓨터에서 달라지는 것은 파일과 도구가 일하는 장소입니다.
폴더를 연결하면 폴더 전체가 클라우드로 올라가나요?
저희가 관찰한 바로는 Claude가 필요한 파일만 골라 작업 공간으로 복사했습니다. 그래도 비밀 파일은 작업 폴더에 두지 마십시오.
웹과 데스크톱의 Chat 대화는 이어지나요?
같은 계정이면 이어집니다. Local 작업과 Code 세션의 이어보기는 방식마다 다르므로 따로 확인하십시오.
사용량은 웹과 데스크톱, Code가 따로 계산되나요?
아닙니다. 모두 하나의 한도로 합산됩니다.
같은 요청을 다시 하면 같은 결과가 나오나요?
매번 조금씩 다릅니다. 똑같은 결과가 필요하면 만드는 프로그램을 저장해 직접 실행하십시오.
GitHub에 올리면 자동으로 사이트가 공개되나요?
아닙니다. 저장소 보관과 웹사이트 배포는 별개의 절차입니다.
AI가 잘못 만든 결과의 책임은 누구에게 있나요?
Owner에게 있습니다. 목적, 검수, 승인에 대한 최종 책임을 사람이 갖고, push, 배포, 제출 같은 바깥으로 나가는 일은 항상 직접 승인하십시오.

집에 가서 혼자 해 보는 순서

한 번에 모든 것을 하려 하지 말고, 아래 순서대로 한 칸씩 해 보십시오. 이 표는 필수 순서가 아니라 확장 예시입니다.

단계해 볼 일확인할 결과
1반복하는 일 하나를 고르고 문제 정의서를 적는다문제 정의서
2웹 Chat에서 요구사항을 네 가지로 구체화한다MVP 요구사항
3웹 Chat 또는 데스크톱 Code로 첫 웹앱을 만든다실행되는 첫 결과
4실제로 써 보고 오류와 불편을 적는다개선 요청
5데스크톱 Code(Local)에서 Manual 모드로 이어서 개발한다테스트된 프로그램
6점검표를 확인하고 GitHub에 올린다보관된 저장소
7같은 결과가 필요한 작업은 프로그램으로 저장한다반복 실행되는 자동화
8IDE에 확장과 CLI를 연결해 역할을 나눈다여러 Agent 협업

처음 목표는 웹페이지 하나가 화면에 나타나는 장면입니다. 그러나 그 장면이 끝은 아닙니다. 내 문제를 말로 정리하고, Claude에게 구현을 맡기고, 결과를 내가 검증하고, 반복 작업을 조금씩 넘겨 가면서 얻은 시간을 내가 중요하게 여기는 배움과 창작과 일에 쓰는 것이 바이브코딩의 목적입니다.

정리: 작게 시작하고, 직접 확인하며, 반복되는 일부터 하나씩 맡겨 나갑니다.
