발표 스크립트 · 3부

바이브코딩으로 만들기 — 웹에서, 그리고 내 컴퓨터에서

2부에서 오늘 우리가 걸어갈 길을 세 계단으로 보았습니다. 채팅창에서 말로 만들어 보기, 내 컴퓨터의 데스크톱 앱으로 고치고 키우기, IDE에서 여러 에이전트에게 나눠 맡기기입니다. 3부는 앞의 두 계단입니다. 늘 쓰던 채팅창에서 프로그램 하나를 만들어 보고, 고치다가 웹의 한계에 부딪히고, 데스크톱 앱으로 옮겨 내 폴더에서 필요한 줄만 고치는 길을 실제 기록으로 따라가 보겠습니다.

1 · 채팅창에서 시작

"10분 타이머 만들어 줘" — 채팅창에서 한 문장이면 시작됩니다

프로그램을 한 번도 만들어 본 적이 없다고 해 보겠습니다. 그런데 수업이나 회의에서 쓸 타이머가 하나 필요해졌습니다. 예전 같으면 인터넷에서 적당한 타이머를 찾거나 이미 만들어진 프로그램을 설치했을 것입니다. 이제는 늘 쓰던 채팅창에 이렇게 쓰면 됩니다.

"10분 타이머를 만들어 줘."

이 한 문장으로 AI는 타이머 코드를 써 줍니다. 화면에 10:00이 뜨고, 시작을 누르면 시간이 줄고, 일시정지를 누르면 멈춥니다. Python이나 JavaScript를 몰라도 됩니다.

여기서는 일부러 캔버스 같은 특별한 기능을 쓰지 않고, 늘 쓰던 일반 채팅창으로 합니다. 오늘 처음 바이브코딩을 해 보시는 분도 지금 쓰고 계신 그 창에서 바로 따라 하실 수 있기 때문입니다.

그런데 써 보면 아쉬운 점이 보입니다. "숫자가 너무 작아. 교실 뒤에서도 보이게 크게 해 줘." AI가 고칩니다. "배경은 검은색, 숫자는 노란색으로 해 줘." 또 고칩니다. "마지막 10초는 빨간색으로 바뀌게 해 줘." 이번에도 고칩니다. 하다 보면 재미가 붙습니다. 처음에는 10분 타이머만 필요했는데, 이제는 5분과 20분도 고르고 싶고, 끝나면 알림음도 울렸으면 좋겠습니다.

이 과정에서 일어나는 일을 눈여겨보십시오. 처음에는 한 문장으로 만들었는데, 써 보면서 새 요구가 계속 생겨납니다. 프로그램 개발에서는 아주 자연스러운 일입니다. 처음부터 모든 요구를 알고 시작하는 사람은 드뭅니다. 써 봐야 무엇이 불편하고 무엇이 더 필요한지 압니다. 작게 만들고, 써 보고, 고치기를 되풀이하는 이 방식을 반복 개발(Iterative Development)이라고 합니다. 바이브코딩은 이 반복 개발을 누구나 해 볼 수 있게 해 주었습니다.

그런데 기능이 늘어나면 이상한 일이 생깁니다. "배경음악을 넣어 줘"라고 했더니 잘 되던 일시정지가 고장 납니다. 일시정지를 고쳐 달라고 했더니 이번에는 끝날 때 울리던 알림음이 사라집니다. 알림음을 다시 넣어 달라고 했더니 화면 배치가 바뀝니다.

왜 그럴까요. 프로그램의 기능들은 서로 이어져 있기 때문입니다. 타이머의 시작, 일시정지, 재시작, 종료 알림은 모두 '남은 시간'이라는 같은 정보를 함께 씁니다. 새 기능을 넣으면서 그 부분을 잘못 건드리면 다른 기능까지 흔들립니다. 이렇게 새것을 고쳤는데 멀쩡하던 옛 기능이 고장 나는 것을 회귀 결함(Regression)이라고 합니다. 사람이 짤 때도 생기는 일입니다. 다만 AI는 한 번에 많이 고치기 때문에, 확인하지 않으면 늦게 알아챕니다.

그래서 할 일이 생깁니다. 먼저 이 프로그램이 어떤 기능을 가져야 하는지 적어 둡니다. 그리고 고칠 때마다 시작, 일시정지, 재시작, 시간 바꾸기, 종료 알림이 그대로 되는지 하나하나 확인합니다. 이것이 테스트입니다.

그러면 AI에게 하는 말도 달라집니다. 처음에는 "만들어 줘"였는데, 이제는 "기존 기능은 그대로 두고 고쳐 줘", "고친 뒤에 모든 기능을 검사해 줘"가 됩니다. 느낌을 전하던 말이 구체적인 작업 지시로 바뀌는 것입니다. 1부에서 말씀드린 '끝까지'가 바로 여기서 시작됩니다.

이 장면은 일반 채팅창에서 타이머를 만들고 고치는 과정을 그대로 녹화한 영상으로 보여 드립니다(새 녹화 앞부분).

프로그램을 만드는 것과, 원하는 프로그램을 제대로 완성하는 것은 다른 문제입니다.

2 · 웹에 차려진 바이브코딩

세 회사는 웹에서 바이브코딩을 이렇게 차려 놓았습니다

채팅창 말고도 웹에는 바이브코딩을 하는 자리가 더 있습니다. 세 회사의 서비스를 써 보면 차려 놓은 모양이 조금씩 다릅니다.

OpenAI와 Anthropic은 둘로 나눠 놓았습니다. 쉬운 것은 ChatGPT와 Claude 채팅창에서 하고, 좀 더 복잡한 것은 코딩 전용인 Codex와 Claude Code에서 합니다. Codex와 Claude Code는 코드를 쓰고, 고치고, 실행해 확인하는 일을 맡는 코딩 에이전트입니다.

Google은 Gemini 채팅창 하나가 쉬운 것부터 알아서 처리하고, 더 전문적인 일은 따로 AI Studio에서 하게 해 두었습니다. AI Studio에는 두 가지 방식이 있습니다.

하나는 Playground입니다. 모델에게 말을 걸어 시험하는 곳으로, "타이머를 HTML 파일 하나로 만들어 줘"라고 하면 파일 한 장을 만들어 줍니다. 웹페이지는 보통 세 가지로 이루어집니다. HTML은 뼈대, CSS는 모양, JavaScript는 버튼이나 타이머 같은 움직임을 맡습니다. 작은 프로그램은 이 셋을 HTML 파일 한 장에 다 넣을 수 있어서, 내려받아 더블클릭하면 웹 브라우저에서 바로 돌아갑니다. 컴퓨터 언어를 한 줄도 쓰지 않았는데 파일 한 장이 프로그램처럼 움직이는 첫 경험을 여기서 하게 됩니다.

다른 하나는 Build Mode입니다. 여기서는 AI가 앱의 구조를 잡고 여러 파일을 함께 만듭니다. 프로그램이 커지면 모든 코드를 파일 하나에 넣기보다 화면, 디자인, 기능, 설정을 파일로 나누는 편이 관리하기 좋습니다. 책 한 권을 긴 문단 하나로 쓰지 않고 장과 절로 나누는 것과 같습니다. Build Mode는 이렇게 나뉜 여러 파일의 코드를 웹에서 다 보여 주고, 미리보기로 바로 써 보게 해 줍니다.

실제로 한글타자연습앱을 Build Mode로 만들어 보았습니다. 미리 써 둔 요구사항 파일 하나와 배경 음악 네 곡을 올리자, AI는 계획을 세우고 화면, 가상 키보드, 연습 세트, 세 언어 번역, 음악 재생, 기록 저장을 각각 다른 파일로 나눠 만들었습니다. 몇 분 만에 미리보기에서 연습할 수 있었습니다. Google 로그인과 학생 기록 저장소를 붙여 달라고 하자 Firebase 프로젝트를 스스로 만들고 연결까지 했습니다. 사람이 한 일은 Google 로그인을 허락하는 것 하나였습니다. 다만 GitHub에 저장소를 만들고 올리는 일은 보안 때문에 사람이 비밀번호를 확인하고 버튼을 눌러야 했습니다.

어느 회사든 웹에서 바로 시작할 수 있습니다. 설치도, 설정도 필요 없습니다. 이것이 웹 바이브코딩의 큰 장점입니다. 문제는 만든 것을 고치고 키울 때 드러납니다.

어느 회사든 웹에서 바로 시작할 수 있습니다. 문제는 고치고 키울 때 드러납니다.

3 · 웹의 구조

웹에서는 두뇌도, 손발도, 작업 공간도 모두 클라우드에 있습니다

문제를 보기 전에, 웹에서 프로그램이 어디서 만들어지는지부터 생각해 보겠습니다. 우리는 웹 브라우저로 서비스에 들어가 "이런 프로그램을 만들어 줘"라고 씁니다. 그 프로그램은 내 컴퓨터에서 만들어질까요?

그렇지 않습니다. 생각하는 AI 모델, 곧 LLM(대규모 언어 모델)은 인터넷 너머 회사의 컴퓨터에서 돌아갑니다. 이것을 클라우드라고 합니다. 내 책상 위 컴퓨터가 아니라 인터넷으로 연결된 서비스 회사의 컴퓨터를 빌려 쓰는 것입니다.

여기서 하나 구분해 둘 것이 있습니다. AI 모델이 모든 일을 직접 하는 것은 아닙니다. 모델은 무엇을 만들지 판단하고 코드를 씁니다. 파일을 만들고 고치고 실행하는 일은 서비스에 연결된 도구가 합니다. 모델이 두뇌라면, 도구는 손발입니다.

웹에서는 이 손발도 서비스 회사의 클라우드에 있습니다. 그리고 손발이 만든 결과물도 서비스 안의 가상 공간에 놓입니다. 내가 보는 것은 결과 화면과 코드뿐이고, 파일은 서비스 안에 있습니다. 그래서 고치려면 다시 말로 시키고, AI는 클라우드 안에서 다시 만들어 보여 줍니다.

처음 만들어 볼 때는 이 구조가 오히려 고맙습니다. 개발 도구를 설치하고 설정하는 데 몇 시간을 쓰지 않고도 원하는 것을 바로 만들어 볼 수 있기 때문입니다.

웹에서는 내가 말하고, AI가 클라우드 안에서 만듭니다. 내 컴퓨터에는 아직 아무것도 없습니다.

4 · 웹의 벽

고칠 때마다 전체를 다시 쓰면, 수정이 쌓일수록 벽에 부딪힙니다

처음 만드는 일과 이미 만든 것을 계속 고치는 일은 성격이 다릅니다. 처음에는 아무것도 없으니 AI가 새로 쓰면 됩니다. 그런데 기능이 열 개, 스무 개로 늘어난 프로그램에서 알림음 하나만 바꾸고 싶다면 어떨까요. 가장 좋은 방법은 잘 되는 아홉 가지는 그대로 두고 알림음을 맡은 코드만 정확히 고치는 것입니다.

그런데 채팅창에서 "이 두 줄만 고쳐 줘"라고 하면, AI는 대개 파일 전체를 다시 써서 보여 줍니다. 그러면 세 가지 손해가 생깁니다. 기다리는 시간이 파일 길이만큼 걸리고, 고쳐 달라고 하지 않은 곳이 바뀌거나 긴 파일의 뒷부분이 잘리고, 앞에서 정한 조건이 슬쩍 빠집니다. 앞에서 본 회귀 결함이 여기서 자꾸 생깁니다.

한글타자연습앱을 웹에서 만들고 고치면서 부딪힌 벽은 다섯 가지였습니다.

  1. 두 줄만 고쳐 달라 해도 파일 전체를 통째로 다시 쓰다가 이전 조건이 빠집니다.
  2. 웹 속 AI는 내 파일에 닿지 못해 내 컴퓨터에 있는 음악이나 이미지를 다루기 어렵습니다.
  3. 미리보기와 실제 배포는 다릅니다. 미리보기에서 되던 앱이 배포하면 멈췄습니다. 음악 버튼이 먹통이 되고, 로그인 창이 0.1초 떴다가 사라졌습니다.
  4. GitHub의 배포 설정이나 Firebase의 승인 도메인처럼 코드 밖에 있는 설정은 웹 속 AI가 만지지 못합니다.
  5. 대화가 길어질수록 AI가 읽어야 할 양이 늘어 비용이 늘고, 앞에서 정한 조건을 놓칩니다.

다섯째는 조금 더 풀어 보겠습니다. AI가 지금 작업을 이해하는 데 쓰는 앞의 대화와 정보를 맥락(Context)이라고 합니다. AI가 한 번에 읽을 수 있는 맥락의 양에는 한계가 있고, 이것을 컨텍스트 윈도우라고 부릅니다. 대화가 길어지면 오래된 조건이 흐려지거나 많은 정보 속에서 중요한 조건을 놓칩니다. 그리고 AI가 읽고 쓰는 글은 토큰이라는 단위로 계산되어, 사용량과 비용도 이 단위로 매겨집니다. 고칠 때마다 전체를 다시 읽고 다시 쓰면 그만큼 토큰이 듭니다.

비유하면 이렇습니다. 전구 하나가 나갔는데 집 전체 배선을 다시 까는 것이 전체 다시 쓰기입니다. 나간 전구 하나만 가는 것이 차이만 고치기(Diff Patch)입니다. 파일이 내 컴퓨터에 있으면 AI가 필요한 줄만 찾아 고칠 수 있습니다.

1부에서 끝까지 만들면 요구사항, 내 업무 규칙이 담긴 프로그램, 결과를 시험하는 눈이 남는다고 말씀드렸습니다. 웹에서 결과물만 받으면 파일 한 장과 화면 한 장이 남고, 다음에 고칠 때는 다시 처음부터입니다. Build Mode처럼 몇 분 만에 웹페이지를 만들어 주는 도구는 분명 대단합니다. 한두 번 쓰고 버릴 결과물이라면 그것으로 충분합니다. 다만 계속 고치고 키울 것이라면, 기준을 "어떤 기능이 되느냐"가 아니라 "만든 뒤에 나에게 무엇이 남느냐"에 두어야 합니다.

이 장면도 새 녹화에 담았습니다. 채팅창에서 고쳐 달라고 할 때마다 코드 전체가 다시 나오는 모습입니다. 웹에서 내 컴퓨터로 옮겨 가는 까닭은 「채팅에서 IDE로」에, 사용량을 아끼는 방법은 Claude 편과 ChatGPT 편에 따로 정리해 두었습니다.

고칠 것은 한 줄인데 매번 전체를 다시 쓰면, 시간과 토큰이 그만큼 듭니다.

5 · 데스크톱 앱으로

내 컴퓨터의 데스크톱 앱으로 옮기면, 필요한 줄만 고칩니다

그래서 둘째 계단으로 올라갑니다. 웹에서 빠르게 만들어 보고, 계속 고치고 키울 것이면 내 컴퓨터로 가져와 데스크톱 앱에서 이어 가는 것입니다.

순서는 간단합니다. 첫째, 웹에서 만든 것을 내려받아 내 컴퓨터의 폴더 하나에 둡니다. 둘째, 데스크톱 앱을 열고 그 폴더를 작업할 곳으로 지정합니다. 셋째, 이렇게 말합니다. "이 폴더의 타이머에서 알림음 부분만 고쳐 줘. 나머지 기능은 그대로 두고, 고친 뒤 모든 기능을 검사해 줘."

그러면 AI는 폴더의 파일을 직접 읽고, 알림음을 맡은 곳을 찾아 그 줄만 고치고, 실행해서 확인합니다. 어느 파일의 어느 줄이 바뀌었는지도 보여 줍니다. 웹에서처럼 파일 전체를 다시 써서 붙여 넣는 일이 없습니다.

데스크톱 앱이라고 하면 낯설게 들리지만, 생김새는 웹과 같은 채팅창입니다. ChatGPT 앱에는 Codex가, Claude 앱에는 Code 탭(Claude Code)이 있습니다. 둘 다 내 컴퓨터에 설치해 쓰고, 웹에서 쓰던 채팅창과 같은 모양이라 처음 써도 어렵지 않습니다.

설치가 걱정되실 수 있습니다. 막히면 그 화면을 캡처해 아무 채팅창에나 보여 주며 "여기서 다음에 뭘 눌러야 해?"라고 물으면 됩니다. 채팅창의 AI가 화면을 보고 한 단계씩 안내해 줍니다. 클릭과 로그인만 내가 하면 됩니다.

여기서 구조가 어떻게 바뀌었는지 보겠습니다. 생각하는 두뇌, 곧 AI 모델은 여전히 회사의 클라우드에 있습니다. 바뀐 것은 손발과 작업 공간입니다. 파일을 읽고 쓰고 명령을 실행하는 손발은 내 컴퓨터의 앱 안에 있고, 작업 공간은 내가 허락한 폴더입니다. 원격으로 전문가에게 일을 맡기되, 허락한 범위 안에서만 내 컴퓨터의 자료를 보고 고치도록 도구를 이어 준 것과 비슷합니다. 그래서 어느 폴더를 허락할지, 무엇을 실행하게 할지는 내가 정해야 합니다.

두 가지를 구분해 두면 좋습니다. 웹에서는 클라우드의 AI가 클라우드의 손발로 클라우드 안 가상 공간에 결과물을 만듭니다. 데스크톱 앱에서는 클라우드의 AI와 이야기하면서, 내 컴퓨터의 손발이 내가 허락한 폴더에 결과물을 만듭니다. 이 차이를 알면 "왜 웹에서는 안 되던 것이 여기서는 되지?"가 풀립니다.

데스크톱 앱의 능력은 써 보면 놀랍습니다. Claude Code에게 한 번 승인했더니 Firebase 로그인과 데이터베이스 설정을 숨 돌릴 틈 없이 끝냈습니다. 웹에서는 사람이 관리 화면을 오가며 해야 했던 코드 밖 설정까지 내 컴퓨터의 손발로 해낸 것입니다.

물론 내 컴퓨터로 옮겼다고 모든 수정이 저절로 정확해지는 것은 아닙니다. 웹 서비스 가운데에도 파일 단위로 고치는 것이 있습니다. 핵심은 클라우드냐 내 컴퓨터냐가 아니라, 만든 것의 구조를 지키며 필요한 곳만 고치고, 바뀐 곳을 확인하고, 시험할 수 있는 자리를 갖추는 것입니다. 그리고 두뇌까지 내 컴퓨터로 들여오는 방법은 5부에서 따로 보겠습니다.

새 녹화의 뒷부분은 이미 설치된 데스크톱 앱을 켜서 내 폴더를 지정하고, 같은 타이머의 필요한 줄만 고치는 장면입니다. Claude 데스크톱 앱의 Claude 탭과 Code 탭이 무엇이 다른지는 영상 「관광대 강의 준비 ② Claude 데스크톱 앱 이해하기」와 「Claude Desktop App [Claude / Code]」에서 볼 수 있습니다.

웹은 가능성을 열어 주고, 내 컴퓨터는 통제권을 줍니다.

6 · 되돌릴 수 있게

망가져도 어제로 돌아갈 수 있게 — Git과 GitHub

내 컴퓨터에서 AI가 파일을 직접 고치게 되면 새 걱정이 생깁니다. "AI가 고치다가 망가뜨리면 어떡하지?" "어제까지 잘 되던 상태로 돌아갈 수는 없을까?"

문서를 만들어 보신 분이라면 이런 경험이 있으실 겁니다. "강의자료_최종", "강의자료_최종수정", "강의자료_진짜최종". 이름을 바꿔 가며 옛 판을 보관하는 일입니다. 프로그램은 파일이 여럿이고 서로 이어져 있어서 이렇게 보관하기가 더 어렵습니다. 그래서 바뀐 내용을 차례로 기록해 두고 언제든 그때로 되돌릴 수 있게 하는 도구를 씁니다. 그것이 Git입니다. 그리고 Git으로 남긴 기록을 온라인에 저장하고 다른 사람과 함께 일하게 해 주는 서비스가 GitHub입니다. 둘은 같은 것이 아닙니다.

명령어는 몰라도 됩니다. "지금 상태를 저장해 줘", "어제 상태로 되돌려 줘"라고 말하면 에이전트가 합니다. AI에게 많이 맡길수록, 되돌릴 수 있는 기록을 먼저 만들어 두는 것이 안전합니다.

1부에서 데이터를 쌓아 두는 일과 다른 사람이 쓸 수 있게 배포하는 일은 뒤에서 차례로 말씀드리겠다고 했습니다. 배포는 여기서 이어집니다. 배포란 내 컴퓨터에서만 열리던 것을 주소 하나로 누구나 열 수 있게 내놓는 일입니다. GitHub에 올린 것은 GitHub Pages라는 무료 서비스로 바로 웹사이트가 됩니다. 이 강연 화면도 그렇게 올려 둔 것입니다. 데이터를 쌓아 두는 일은 다음 절의 한글타자연습앱에서 보겠습니다.

돌아보면 이 길은 처음부터 정해진 공부 순서가 아니었습니다. 10분 타이머 하나를 만들다가 요구사항이 생겼고, 오류를 만나 테스트가 필요해졌고, 파일이 늘어 내 컴퓨터로 옮겼고, 망가질까 봐 Git을 쓰게 되었습니다. 예전에는 프로그래밍 언어부터 배워야 원하는 것을 만들 수 있었습니다. 지금은 원하는 것을 먼저 만들어 보면서, 필요한 개념을 궁금한 순서대로 하나씩 배웁니다. 기본 원리를 배우는 일이 없어지는 것은 아닙니다. 오히려 내가 만든 것에서 문제가 생기면 그 원리를 더 알고 싶어집니다.

Git과 GitHub를 사진첩에 빗대어 풀어 쓴 읽을거리 「git과 GitHub, 사진첩으로 이해하기」가 있습니다. 저장, 올리기와 내려받기, 배포, 다른 배포 사이트까지 AI에게 할 말과 함께 정리했습니다.

AI에게 많이 맡길수록, 되돌릴 수 있는 기록이 먼저입니다.

7 · 같은 요구, 세 가지 길

같은 요구, 세 가지 길 — 한글타자연습앱

웹과 데스크톱 앱의 차이를 실제로 보려고, 같은 요구사항에서 출발해 한글타자연습앱을 세 가지 길로 만들어 배포까지 가 보았습니다. 외국인 유학생이 한컴타자연습에 들어가기 전에 글쇠 자리를 손가락에 익히는 연습 앱입니다.

②는 웹에서 맛본 것을 내 컴퓨터에서 키우는 길이 그대로 담겨 있습니다. AI Studio Playground에서 만든 HTML 파일 한 장을 내 폴더에 두고, Claude 데스크톱 앱의 Claude Code에게 맡겼습니다. Claude Code는 한 장짜리 앱을 화면, 자판, 연습 세트, 언어 파일로 나누고 기록 저장과 배경 음악을 붙였습니다. GitHub 설정은 내 브라우저를 대신 조작해 처리했고, Firebase 프로젝트를 만들어 Google 로그인과 기록 저장소, 남의 기록을 함부로 고치지 못하게 막는 보안 규칙까지 적용했습니다. 사람은 로그인 같은 단계만 직접 했습니다.

③은 빈 폴더에서 시작해 Codex에게 맡긴 기록으로, 1부에서 자세히 본 그 장면입니다. 처음 만드는 데 약 14분, 원하는 대로 될 때까지 시험하고 고치는 데 그 열 배 가까운 시간이 들었습니다. 점수를 어떻게 매길지처럼 수업을 아는 사람만 정할 수 있는 것은 사람이 정했습니다.

여기서 1부에서 미뤄 둔 또 하나, 데이터를 쌓아 두는 일이 나옵니다. 학생 기록처럼 쌓이는 자료를 모아 두는 저장소를 데이터베이스(DB)라고 합니다. 이 앱에서는 Google의 앱 뒷단 서비스인 Firebase를 써서, 로그인(Authentication)으로 누가 들어왔는지 확인하고, 기록 저장소(Firestore)에 학생별 연습 기록을 모았습니다. 어느 컴퓨터에서 열어도 같은 기록이 보이고, 순위표도 이 기록으로 만듭니다.

세 편은 같은 조건에서 겨룬 시험이 아닙니다. 같은 요구에서 출발해, 도구마다 사람과 AI가 각각 무엇을 했는지 나란히 본 기록입니다. 셋 다 해냈습니다. 차이는 처음 만들 때가 아니라 고치고 키울 때 드러났습니다.

8 · 하나의 앱으로 만든 것

데스크톱 앱 하나로 이런 것까지 만들었습니다

데스크톱 앱 하나, 에이전트 하나로 어디까지 할 수 있는지 실제로 만든 것 세 가지를 보여 드리겠습니다.

첫째는 앞에서 본 한글타자연습 웹페이지입니다. Codex 데스크톱 앱 하나로 연습 화면을 만들고, 로그인과 순위표를 더하고, 배포해 학생들이 주소 하나로 쓰게 했습니다.

둘째는 관광대 강의 자료 웹사이트입니다. 외국인 유학생 6주 강의 자료를 HTML 파일로 만들어 둔 폴더가 있었습니다. Claude 데스크톱 앱의 Claude Code에게 "학생들이 볼 수 있게 인터넷에 올려 달라"고 하자, GitHub 저장소를 만들고 GitHub Pages로 배포했습니다. 눈여겨볼 장면이 하나 있습니다. 내용이 빈 3차시 파일을 AI가 스스로 찾아 공개에서 빼고 따로 보관한 뒤, 계획표에는 "준비 중"이라고 적었습니다. 시키는 대로 다 올리지 않고 공개하면 안 되는 것을 먼저 걸러 낸 것입니다. 이제 학생들은 주소 하나로, 베트남어나 미얀마어로 바꿔 가며 강의 자료를 봅니다.

셋째는 오늘 보시는 영상들을 만든 도구입니다. AI와 함께 일하는 화면을 녹화하면 화면이 멈춰 있거나 AI의 답을 기다리는 시간이 대부분입니다. 영상 13편을 만든 녹화본을 다 합치면 44시간 19분이었습니다. 이것을 4시간 28분으로 줄였습니다.

멈춘 화면을 자르는 무거운 일은 내 컴퓨터의 무료 영상 프로그램(ffmpeg)이 합니다. 0.5초마다 화면이 얼마나 바뀌는지 재서, 3초 넘게 멈춘 곳은 자르고, AI가 생각하는 동안은 12배속, 글자가 출력되는 동안은 4배속으로 넘깁니다. 먼저 영상마다 원본과 결과 길이를 적은 길이표를 보여 주고, 사람이 승인하면 그때 영상을 만듭니다. AI는 44시간 영상을 직접 보는 것이 아니라 이 프로그램이 낸 숫자를 보고 판단하므로, AI 사용량은 거의 들지 않았습니다. 웹에서 해 보려 했더니 큰 영상 파일을 올리는 데만 오랜 시간이 걸렸습니다. 무거운 자료는 자료가 있는 내 컴퓨터에서 처리하는 것이 맞았습니다. 웹과 데스크톱 앱의 차이가 여기서도 드러납니다.

AI가 맡은 것은 판단이 필요한 곳이었습니다. 실수나 같은 일의 반복처럼 뺄 장면을 고르고, 장면을 보고 지금 무슨 일을 하는지 설명 자막을 쓰고, 그 자막을 무료 음성으로 읽혀 나레이션을 만들었습니다. 사람이 한 일은 녹화, 컷편집 계획 승인, 장면 확인, 목소리 고르기, 제목과 배경음악과 썸네일, 그리고 공개 여부 판단이었습니다.

세 가지 모두 만든 AI는 하나였고, 무엇을 시험하고 어디를 고칠지 알려 준 것은 사람이었습니다. 어느 것이든 마지막 확인은 그것을 쓸 사람이 했습니다. 일이 이만한 크기라면 에이전트 하나, 데스크톱 앱 하나로 충분합니다.

영상: 한글타자연습앱 ③ Codex · 관광대 ① 강의 자료를 웹사이트로 · 44시간 녹화를 4시간으로

일이 이만한 크기라면, 에이전트 하나와 데스크톱 앱 하나로 충분합니다.

그런데 일이 더 커지면 어떨까요. 기획하고, 만들고, 검토하는 일을 에이전트 하나가 다 해도 괜찮을까요. 한 회사의 에이전트가 만든 것을 다른 회사의 에이전트에게 검토하게 하면 무슨 일이 생길까요. 4부에서 셋째 계단, 여러 에이전트로 이어 가겠습니다.
