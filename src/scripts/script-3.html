발표 스크립트 · 3부

바이브코딩으로 만들기 — 웹에서, 그리고 내 컴퓨터에서

2부에서 오늘 우리가 걸어갈 길을 세 계단으로 보았습니다. 채팅창에서 말로 만들어 보기, 내 컴퓨터의 데스크톱 앱으로 고치고 키우기, IDE에서 여러 에이전트에게 나눠 맡기기입니다. 3부는 앞의 두 계단입니다. 늘 쓰던 채팅창에서 프로그램 하나를 만들어 보고, 고치다가 웹의 한계에 부딪히고, 데스크톱 앱으로 옮겨 내 폴더에서 필요한 줄만 고치는 길을 실제 기록으로 따라가 보겠습니다.

1 · 채팅창에서 시작

"10분 타이머 만들어 줘" — 한 문장이면 어느 AI든 만들어 줍니다

수업이나 회의에서 쓸 타이머가 하나 필요해졌다고 해 보겠습니다. 예전 같으면 인터넷에서 적당한 타이머를 찾거나 이미 만들어진 프로그램을 설치했을 것입니다. 이제는 늘 쓰던 AI 창에 이렇게 쓰면 됩니다.

"10분 타이머 만들어 줘."

이 한 문장을 일곱 곳에 똑같이 넣어 보았습니다. ChatGPT의 채팅과 Work 모드와 Codex, Claude의 채팅과 Claude Code, Gemini, 그리고 Google AI Studio의 Playground와 Build mode입니다. 어느 곳이든 조건 없이 한 줄만 넣었는데 돌아가는 타이머를 만들어 주었습니다. 시작, 일시정지, 알림음처럼 말하지 않은 것까지 알아서 넣어 주었습니다.

이어서 원하는 것을 말로 더했습니다. 숫자를 교실 뒤에서도 보이게 아주 크게, 검은 바탕에 노란 숫자로 해 달라고 했습니다. 마지막 10초는 빨간색으로 바뀌고, 1분·5분·10분·20분을 고르는 버튼을 넣고, 끝나면 알림음이 울리게 해 달라고 했습니다. 배경은 지금 계절에 맞는 그림으로 바꿔 달라고 했습니다. 말하는 대로 다 만들어 주었습니다. 늦가을 풍경을 코드로 직접 그린 곳도 있었고, 배경 사진을 직접 만들어 넣은 곳도 있었습니다.

이 과정에서 코드는 한 줄도 쓰지 않았습니다. Python이나 JavaScript를 전혀 몰라도 됩니다. 원하는 것을 정확하게 말하면 AI가 다 만들어 줍니다.

일곱 곳에서 해 본 것은 어느 AI가 더 나은지 순위를 매기려는 것이 아닙니다. 어느 회사의 어느 창이든, 말로 하면 프로그램을 만들어 주는 때가 되었다는 것을 보여 드리려는 것입니다. 이것이 바이브코딩의 첫 번째 방법입니다.

이제는 어느 AI든, 늘 쓰던 창에서 말로 하면 프로그램을 만들어 줍니다.

2 · 웹에서 바이브코딩 하는 곳

웹에서 바이브코딩을 한다면, 회사마다 이런 곳을 씁니다

채팅창 말고도 웹에는 바이브코딩을 할 수 있는 곳이 더 있습니다. 세 회사를 써 보면, 쉬운 것과 복잡한 것을 어디서 하는지가 조금씩 다릅니다.

ChatGPT와 Claude는 들어가는 창이 나뉘어 있습니다. 쉬운 것은 채팅창에서 하고, 좀 더 복잡한 것은 코딩 전용인 Codex와 Claude Code에서 합니다. Codex와 Claude Code는 코드를 쓰고, 고치고, 실행해 확인하는 일을 맡는 코딩 에이전트입니다.

Gemini는 다릅니다. 코딩 전용 창을 따로 두지 않고, 입력은 한 창에서 받습니다. 그리고 그것이 가벼운 대화인지, 코드를 만드는 일인지는 안에서 알아서 나눠 처리합니다. 내가 창을 고를 필요가 없는 셈입니다. 더 전문적인 일은 따로 AI Studio에서 하게 해 두었는데, 여기에는 두 가지 방식이 있습니다.

하나는 Playground입니다. 모델에게 말을 걸어 시험해 보는 곳으로, 타이머를 만들어 달라고 하면 HTML 파일 한 장으로 만들어 줍니다. 웹페이지는 보통 뼈대를 맡는 HTML, 모양을 맡는 CSS, 버튼이나 타이머 같은 움직임을 맡는 JavaScript, 이 세 가지로 이루어지는데, 작은 프로그램은 이 셋을 한 장에 다 담을 수 있습니다. 그래서 내려받아 더블클릭하면 웹 브라우저에서 바로 돌아갑니다.

편리하지만 눈여겨볼 점이 있습니다. 모든 것이 한 장에 들어 있으니, 배경 하나만 고쳐 달라고 해도 AI는 그 한 장 전체를 처음부터 다시 씁니다. 채팅창도 마찬가지입니다. 고칠 때마다 전체를 다시 쓰면 그만큼 시간과 토큰이 듭니다. 이 점은 뒤에서 데스크톱 앱으로 옮겨 가는 까닭이 됩니다.

다른 하나는 Build Mode입니다. 여기서도 모든 처리는 클라우드에서 하고, 나는 웹페이지에서 결과를 봅니다. 다른 점은 AI가 앱의 구조를 잡고 화면, 디자인, 기능, 설정을 여러 파일로 나눠 만든다는 것입니다. 책 한 권을 긴 문단 하나로 쓰지 않고 장과 절로 나누는 것과 같습니다. 타이머는 일곱 곳 가운데 Build Mode가 가장 잘 만들었습니다. 설정 화면과 배경까지 한 번에 거의 다 맞췄고, 끝날 때 캐럴을 울려 달라고 하자 바뀌어야 할 파일만 골라 고쳤습니다.

그런데 내려받을 때 일이 생겼습니다. 받은 압축 파일을 풀어 index.html을 열었더니 빈 화면만 나왔습니다. Build Mode의 앱은 React와 Vite로 만들어져, 여러 부품 파일을 도구로 조립해야 돌아가기 때문입니다. 고쳐 달라고 하자 Build Mode는 더블클릭으로 바로 여는 한 장짜리 HTML 파일을 따로 만들어 주었습니다. 다만 처음 받은 파일에는 기능이 일부만 줄여 담겨 있었고, 다시 요구하자 그제야 모든 기능을 담은 파일을 주었습니다. AI Studio는 이것을, 나뉜 파일은 설계도와 부품이고 한 장짜리 파일은 시동만 걸면 되는 완성차라고 비유했습니다.

어느 회사든 웹에서 바로 시작할 수 있습니다. 설치도, 설정도 필요 없습니다. 이것이 웹 바이브코딩의 큰 장점입니다. 문제는 만든 것을 고치고 키울 때 드러납니다.

어느 회사든 웹에서 바로 시작할 수 있습니다. 문제는 고치고 키울 때 드러납니다.

3 · 좀 더 복잡한 앱

같은 요구, 세 가지 길 — 한글타자연습앱

타이머처럼 간단한 것은 한 줄이면 어디서든 만들어 줍니다. 그렇다면 로그인과 순위표, 배포까지 있는 좀 더 복잡한 앱은 어떨까요. 외국인 유학생이 한컴타자연습에 들어가기 전에 글쇠 자리를 손가락에 익히는 한글타자연습앱으로 해 보았습니다.

복잡한 앱은 프롬프트부터 준비해야 합니다. 그런데 처음부터 완벽한 프롬프트를 쓸 수 있는 사람은 없습니다. 이 앱의 요구사항은 사흘에 걸쳐 만들었습니다. 운전하면서도 채팅 AI에게 말로 만들고 싶은 것을 설명했고, 도착해서는 지금까지 한 말을 요약해 달라고 했습니다. 그 요약을 다시 채팅창에 넣고 이어서 요구를 더해 가며 맥락을 쌓았습니다. 그렇게 채팅 AI가 정리해 준 프롬프트는 1만 5천 자에서 2만 8천 자에 이릅니다. 이렇게 요구사항을 프롬프트로 정리해 주는 채팅 AI를 저는 바이브 에이전트라고 부릅니다.

여기서 1부의 이야기와 만납니다. 무엇을 만들지 말로 풀어낼 수 있는 것은 그 일을 아는 사람입니다. 이 앱이라면 외국인 학생이 어디서 막히는지 아는 사람입니다. 그리고 결과를 받았을 때 제대로 만들어졌는지 알아보고, 고쳐 달라고 할 수 있는 것도 같은 사람입니다. 이렇게 만든 요구사항을 서로 다른 세 도구에 맡겨 배포까지 가 보았습니다. 잘 되는 점과 문제점을 찾아보려는 것이었습니다.

②는 웹에서 맛본 것을 내 컴퓨터에서 키우는 길이 그대로 담겨 있습니다. AI Studio Playground에서 만든 HTML 파일 한 장을 내 폴더에 두고, Claude 데스크톱 앱의 Claude Code에게 맡겼습니다. Claude Code는 한 장짜리 앱을 화면, 자판, 연습 세트, 언어 파일로 나누고 기록 저장과 배경 음악을 붙였습니다. GitHub 설정은 내 브라우저를 대신 조작해 처리했고, Firebase 프로젝트를 만들어 Google 로그인과 기록 저장소, 남의 기록을 함부로 고치지 못하게 막는 보안 규칙까지 적용했습니다. 사람은 로그인 같은 단계만 직접 했습니다.

③은 빈 폴더에서 시작해 Codex에게 맡긴 기록으로, 1부에서 자세히 본 그 장면입니다. 처음 만드는 데 약 14분, 원하는 대로 될 때까지 시험하고 고치는 데 그 열 배 가까운 시간이 들었습니다. 점수를 어떻게 매길지처럼 수업을 아는 사람만 정할 수 있는 것은 사람이 정했습니다.

여기서 1부에서 미뤄 둔 또 하나, 데이터를 쌓아 두는 일이 나옵니다. 학생 기록처럼 쌓이는 자료를 모아 두는 저장소를 데이터베이스(DB)라고 합니다. 이 앱에서는 Google의 앱 뒷단 서비스인 Firebase를 써서, 로그인(Authentication)으로 누가 들어왔는지 확인하고, 기록 저장소(Firestore)에 학생별 연습 기록을 모았습니다. 어느 컴퓨터에서 열어도 같은 기록이 보이고, 순위표도 이 기록으로 만듭니다.

세 편은 같은 조건에서 겨룬 시험이 아닙니다. 같은 요구에서 출발해, 도구마다 사람과 AI가 각각 무엇을 했는지 나란히 본 기록입니다. 셋 다 해냈습니다. 차이는 처음 만들 때가 아니라 고치고 키울 때 드러났습니다. 먼저 ①을 웹에서 고치고 키우며 부딪힌 문제부터 보겠습니다.

4 · 웹의 구조

웹에서는 두뇌도, 손발도, 작업 공간도 모두 클라우드에 있습니다

문제를 보기 전에, 웹에서 프로그램이 어디서 만들어지는지부터 생각해 보겠습니다. 우리는 웹 브라우저로 서비스에 들어가 "이런 프로그램을 만들어 줘"라고 씁니다. 그 프로그램은 내 컴퓨터에서 만들어질까요?

그렇지 않습니다. 생각하는 AI 모델, 곧 LLM(대규모 언어 모델)은 인터넷 너머 회사의 컴퓨터에서 돌아갑니다. 이것을 클라우드라고 합니다. 내 책상 위 컴퓨터가 아니라 인터넷으로 연결된 서비스 회사의 컴퓨터를 빌려 쓰는 것입니다.

여기서 하나 구분해 둘 것이 있습니다. AI 모델이 모든 일을 직접 하는 것은 아닙니다. 모델은 무엇을 만들지 판단하고 코드를 씁니다. 파일을 만들고 고치고 실행하는 일은 서비스에 연결된 도구가 합니다. 모델이 두뇌라면, 도구는 손발입니다.

웹에서는 이 손발도 서비스 회사의 클라우드에 있습니다. 그리고 손발이 만든 결과물도 서비스 안의 가상 공간에 놓입니다. 채팅으로 시킨 프로그램은 클라우드에서 만들어지고, 웹 화면은 그것을 비춰 줄 뿐입니다. 내 컴퓨터에 있는 것이 아닙니다. 그래서 고치려면 다시 말로 요구하고, AI가 클라우드에서 고쳐 다시 보여 줍니다.

처음 만들어 볼 때는 이 구조가 오히려 고맙습니다. 개발 도구를 설치하고 설정하는 데 몇 시간을 쓰지 않고도 원하는 것을 바로 만들어 볼 수 있기 때문입니다.

웹에서는 내가 말하고, AI가 클라우드 안에서 만듭니다. 내 컴퓨터에는 아직 아무것도 없습니다.

5 · 웹의 벽

고칠 때마다 전체를 다시 쓰면, 수정이 쌓일수록 벽에 부딪힙니다

처음 만드는 일과 이미 만든 것을 계속 고치는 일은 성격이 다릅니다. 처음에는 아무것도 없으니 AI가 새로 쓰면 됩니다. 그런데 기능이 열 개, 스무 개로 늘어난 프로그램에서 알림음 하나만 바꾸고 싶다면 어떨까요. 가장 좋은 방법은 잘 되는 아홉 가지는 그대로 두고 알림음을 맡은 코드만 정확히 고치는 것입니다.

그런데 채팅창에서 "이 두 줄만 고쳐 줘"라고 하면, AI는 대개 파일 전체를 다시 써서 보여 줍니다. 그러면 세 가지 손해가 생깁니다. 기다리는 시간이 파일 길이만큼 걸리고, 고쳐 달라고 하지 않은 곳이 바뀌거나 긴 파일의 뒷부분이 잘리고, 앞에서 정한 조건이 슬쩍 빠집니다. 타이머 영상에서도 ChatGPT는 두 가지만 고쳐 달라 했는데 "아래 코드로 통째로 교체해서 쓰시면 됩니다"라고 답했습니다.

앞에서 본 ① Build Mode로 한글타자연습앱을 고치고 키우면서 부딪힌 벽은 다섯 가지였습니다.

  1. 두 줄만 고쳐 달라 해도 파일 전체를 통째로 다시 쓰다가 이전 조건이 빠집니다. 한글타자연습앱을 Build Mode에서 고칠 때 실제로 겪은 일입니다. 배경 음악이 안 나와서 "음악이 안 나와, 고쳐 줘"라고 했습니다. 음악은 나오게 됐습니다. 그런데 로그인 버튼을 누르자 Google 로그인 창이 번쩍 떴다가 0.1초 만에 사라졌습니다. 조금 전까지 잘 되던 기능이고, 로그인에 대해서는 한마디도 하지 않았습니다. 학생이 보면 로그인 버튼이 고장 난 것으로만 보입니다. 원인은 AI가 음악을 고치면서 화면을 맡은 코드 전체를 새로 썼고, 그때 로그인 상태를 붙잡아 두는 코드 몇 줄을 빠뜨린 것이었습니다. 음악 한 줄을 고치려다 로그인이 깨진 셈입니다.
  2. 웹 속 AI는 내 파일에 닿지 못해 내 컴퓨터에 있는 음악이나 이미지를 다루기 어렵습니다.
  3. 미리보기와 실제 배포는 다릅니다. 미리보기에서 되던 앱이 GitHub에 배포하자 로그인이 되지 않았고, 배경 음악도 나오지 않았습니다. 로그인은 Firebase가 허락한 주소에서만 받기 때문이었고, 새 배포 주소를 Firebase에 직접 등록해야 했습니다. 음악은 배포 주소에 맞게 파일 경로를 고쳐서야 나왔습니다.
  4. GitHub의 배포 설정이나 Firebase의 승인 도메인처럼 코드 밖에 있는 설정은 웹 속 AI가 만지지 못합니다.
  5. 대화가 길어질수록 AI가 읽어야 할 양이 늘어 비용이 늘고, 앞에서 정한 조건을 놓칩니다.

다섯째는 조금 더 풀어 보겠습니다. AI가 지금 작업을 이해하는 데 쓰는 앞의 대화와 정보를 맥락(Context)이라고 합니다. AI가 한 번에 읽을 수 있는 맥락의 양에는 한계가 있고, 이것을 컨텍스트 윈도우라고 부릅니다. 대화가 길어지면 오래된 조건이 흐려지거나 많은 정보 속에서 중요한 조건을 놓칩니다. 그리고 AI가 읽고 쓰는 글은 토큰이라는 단위로 계산되어, 사용량과 비용도 이 단위로 매겨집니다. 고칠 때마다 전체를 다시 읽고 다시 쓰면 그만큼 토큰이 듭니다.

비유하면 이렇습니다. 전구 하나가 나갔는데 집 전체 배선을 다시 까는 것이 전체 다시 쓰기입니다. 나간 전구 하나만 가는 것이 차이만 고치기(Diff Patch)입니다. 파일이 내 컴퓨터에 있으면 AI가 필요한 줄만 찾아 고칠 수 있습니다.

1부에서 끝까지 만들면 요구사항, 내 업무 규칙이 담긴 프로그램, 결과를 시험하는 눈이 남는다고 말씀드렸습니다. 웹에서 결과물만 받으면 파일 한 장과 화면 한 장이 남고, 다음에 고칠 때는 다시 처음부터입니다. Build Mode처럼 몇 분 만에 웹페이지를 만들어 주는 도구는 분명 대단합니다. 한두 번 쓰고 버릴 결과물이라면 그것으로 충분합니다. 다만 계속 고치고 키울 것이라면, 기준을 "어떤 기능이 되느냐"가 아니라 "만든 뒤에 나에게 무엇이 남느냐"에 두어야 합니다.

웹에서 내 컴퓨터로 옮겨 가는 까닭은 「채팅에서 IDE로」에, 사용량을 아끼는 방법은 Claude 편과 ChatGPT 편에 따로 정리해 두었습니다.

고칠 것은 한 줄인데 매번 전체를 다시 쓰면, 시간과 토큰이 그만큼 듭니다.

6 · 데스크톱 앱으로

내 컴퓨터의 데스크톱 앱으로 옮기면, 필요한 줄만 고칩니다

그래서 둘째 계단으로 올라갑니다. 웹에서 빠르게 만들어 보고, 계속 고치고 키울 것이면 내 컴퓨터로 가져와 데스크톱 앱에서 이어 가는 것입니다.

한글타자연습앱 ②가 바로 이 길입니다. 첫째, AI Studio Playground에서 받은 HTML 파일 한 장을 내 컴퓨터의 폴더 하나에 둡니다. 둘째, Claude 데스크톱 앱을 열고 그 폴더를 작업할 곳으로 지정합니다. 셋째, 하고 싶은 것을 말합니다. 그러면 AI는 폴더의 파일을 직접 읽고, 필요한 곳만 고치고, 실행해서 확인합니다. 어느 파일의 어느 줄이 바뀌었는지도 보여 줍니다. 웹에서처럼 파일 전체를 다시 써서 붙여 넣는 일이 없습니다. ③ Codex는 빈 폴더에서 시작해 같은 방식으로 일했습니다.

데스크톱 앱이라고 하면 낯설게 들리지만, 생김새는 웹과 같은 채팅창입니다. ChatGPT 앱에는 Codex가, Claude 앱에는 Code 탭(Claude Code)이 있습니다. 둘 다 내 컴퓨터에 설치해 쓰고, 웹에서 쓰던 채팅창과 같은 모양이라 처음 써도 어렵지 않습니다.

말로 설명하기 어려운 것은 보여 주면 됩니다. 화면이 이상하면 캡처해서, 오류 메시지가 나오면 그 글을 복사해서 붙여 넣으면 AI가 잘 알아듣고 고칩니다. 바이브코딩에서 가장 많이 하는 일이 바로 이것입니다. 데스크톱 앱을 설치하다 막힐 때도 같습니다. 그 화면을 캡처해 아무 채팅창에나 보여 주며 "여기서 다음에 뭘 눌러야 해?"라고 물으면, AI가 화면을 보고 한 단계씩 안내해 줍니다. 클릭과 로그인만 내가 하면 됩니다.

여기서 구조가 어떻게 바뀌었는지 보겠습니다. 생각하는 두뇌, 곧 AI 모델은 여전히 회사의 클라우드에 있습니다. 바뀐 것은 손발과 작업 공간입니다. 파일을 읽고 쓰고 명령을 실행하는 손발은 내 컴퓨터의 앱 안에 있고, 작업 공간은 내가 허락한 폴더입니다. 원격으로 전문가에게 일을 맡기되, 허락한 범위 안에서만 내 컴퓨터의 자료를 보고 고치도록 도구를 이어 준 것과 비슷합니다. 그래서 어느 폴더를 허락할지, 무엇을 실행하게 할지는 내가 정해야 합니다.

두 가지를 구분해 두면 좋습니다. 웹에서는 클라우드의 AI가 클라우드의 손발로 클라우드 안 가상 공간에 결과물을 만듭니다. 데스크톱 앱에서는 클라우드의 AI와 이야기하면서, 내 컴퓨터의 손발이 내가 허락한 폴더에 결과물을 만듭니다. 이 차이를 알면 "왜 웹에서는 안 되던 것이 여기서는 되지?"가 풀립니다.

②에서 본 것처럼, 웹에서는 사람이 관리 화면을 오가며 해야 했던 GitHub와 Firebase 설정 같은 코드 밖의 일까지 데스크톱 앱은 내 컴퓨터의 손발로 해냅니다.

물론 내 컴퓨터로 옮겼다고 모든 수정이 저절로 정확해지는 것은 아닙니다. 웹 서비스 가운데에도 파일 단위로 고치는 것이 있습니다. 핵심은 클라우드냐 내 컴퓨터냐가 아니라, 만든 것의 구조를 지키며 필요한 곳만 고치고, 바뀐 곳을 확인하고, 시험할 수 있는 자리를 갖추는 것입니다. 그리고 두뇌까지 내 컴퓨터로 들여오는 방법은 5부에서 따로 보겠습니다.

웹과 데스크톱 앱에서 무엇이 되고 무엇이 공유되는지는 「Claude 웹·앱 비교와 문맥 관리」와 「ChatGPT 웹·앱 비교와 문맥 관리」에 정리해 두었습니다.

웹에서는 결과를 받아 보고, 내 컴퓨터에서는 원본을 내 손에 두고 고칩니다.

7 · 되돌릴 수 있게

망가져도 어제로 돌아갈 수 있게 — Git과 GitHub

내 컴퓨터에서 AI가 파일을 직접 고치게 되면 새 걱정이 생깁니다. "AI가 고치다가 망가뜨리면 어떡하지?" "어제까지 잘 되던 상태로 돌아갈 수는 없을까?"

문서를 만들어 보신 분이라면 이런 경험이 있으실 겁니다. "강의자료_최종", "강의자료_최종수정", "강의자료_진짜최종". 이름을 바꿔 가며 옛 판을 보관하는 일입니다. 프로그램은 파일이 여럿이고 서로 이어져 있어서 이렇게 보관하기가 더 어렵습니다. 그래서 바뀐 내용을 차례로 기록해 두고 언제든 그때로 되돌릴 수 있게 하는 도구를 씁니다. 그것이 Git입니다. 그리고 Git으로 남긴 기록을 온라인에 저장하고 다른 사람과 함께 일하게 해 주는 서비스가 GitHub입니다. 둘은 같은 것이 아닙니다.

명령어는 몰라도 됩니다. "지금 상태를 저장해 줘", "어제 상태로 되돌려 줘"라고 말하면 에이전트가 합니다. AI에게 많이 맡길수록, 되돌릴 수 있는 기록을 먼저 만들어 두는 것이 안전합니다.

1부에서 데이터를 쌓아 두는 일과 다른 사람이 쓸 수 있게 배포하는 일은 뒤에서 차례로 말씀드리겠다고 했습니다. 배포는 여기서 이어집니다. 배포란 내 컴퓨터에서만 열리던 것을 주소 하나로 누구나 열 수 있게 내놓는 일입니다. GitHub에 올린 것은 GitHub Pages라는 무료 서비스로 바로 웹사이트가 됩니다. 이 강연 화면도 그렇게 올려 둔 것입니다. 데이터를 쌓아 두는 일은 앞의 한글타자연습앱에서 보았습니다.

돌아보면 이 길은 처음부터 정해진 공부 순서가 아니었습니다. 10분 타이머는 말 한마디로 만들었고, 더 복잡한 앱을 만들려니 요구사항이 필요했고, 고치고 키우다 웹의 벽을 만나 내 컴퓨터로 옮겼고, 망가질까 봐 Git을 쓰게 되었습니다. 예전에는 프로그래밍 언어부터 배워야 원하는 것을 만들 수 있었습니다. 지금은 원하는 것을 먼저 만들어 보면서, 필요한 개념을 궁금한 순서대로 하나씩 배웁니다. 기본 원리를 배우는 일이 없어지는 것은 아닙니다. 오히려 내가 만든 것에서 문제가 생기면 그 원리를 더 알고 싶어집니다.

Git과 GitHub를 사진첩에 빗대어 풀어 쓴 읽을거리 「git과 GitHub, 사진첩으로 이해하기」가 있습니다. 저장, 올리기와 내려받기, 배포, 다른 배포 사이트까지 AI에게 할 말과 함께 정리했습니다.

AI에게 많이 맡길수록, 되돌릴 수 있는 기록이 먼저입니다.

8 · 하나의 앱으로 만든 것

데스크톱 앱 하나로 이런 것까지 만들었습니다

데스크톱 앱 하나, 에이전트 하나로 어디까지 할 수 있는지 실제로 만든 것 세 가지를 보여 드리겠습니다.

첫째는 앞에서 본 한글타자연습 웹페이지입니다. Codex 데스크톱 앱 하나로 연습 화면을 만들고, 로그인과 순위표를 더하고, 배포해 학생들이 주소 하나로 쓰게 했습니다.

둘째는 관광대 강의 자료 웹사이트입니다. 외국인 유학생 6주 강의 자료를 HTML 파일로 만들어 둔 폴더가 있었습니다. Claude 데스크톱 앱의 Claude Code에게 "학생들이 볼 수 있게 인터넷에 올려 달라"고 하자, GitHub 저장소를 만들고 GitHub Pages로 배포했습니다. 눈여겨볼 장면이 하나 있습니다. 내용이 빈 3차시 파일을 AI가 스스로 찾아 공개에서 빼고 따로 보관한 뒤, 계획표에는 "준비 중"이라고 적었습니다. 시키는 대로 다 올리지 않고 공개하면 안 되는 것을 먼저 걸러 낸 것입니다. 이제 학생들은 주소 하나로, 베트남어나 미얀마어로 바꿔 가며 강의 자료를 봅니다.

셋째는 오늘 보시는 영상들을 만든 도구입니다. AI와 함께 일하는 화면을 녹화하면 화면이 멈춰 있거나 AI의 답을 기다리는 시간이 대부분입니다. 영상 13편을 만든 녹화본을 다 합치면 44시간 19분이었습니다. 이것을 4시간 28분으로 줄였습니다.

멈춘 화면을 자르는 무거운 일은 내 컴퓨터의 무료 영상 프로그램(ffmpeg)이 합니다. 0.5초마다 화면이 얼마나 바뀌는지 재서, 3초 넘게 멈춘 곳은 자르고, AI가 생각하는 동안은 12배속, 글자가 출력되는 동안은 4배속으로 넘깁니다. 먼저 영상마다 원본과 결과 길이를 적은 길이표를 보여 주고, 사람이 승인하면 그때 영상을 만듭니다. AI는 44시간 영상을 직접 보는 것이 아니라 이 프로그램이 낸 숫자를 보고 판단하므로, AI 사용량은 거의 들지 않았습니다. 웹에서 해 보려 했더니 큰 영상 파일을 올리는 데만 오랜 시간이 걸렸습니다. 무거운 자료는 자료가 있는 내 컴퓨터에서 처리하는 것이 맞았습니다. 웹과 데스크톱 앱의 차이가 여기서도 드러납니다.

AI가 맡은 것은 판단이 필요한 곳이었습니다. 실수나 같은 일의 반복처럼 뺄 장면을 고르고, 장면을 보고 지금 무슨 일을 하는지 설명 자막을 쓰고, 그 자막을 무료 음성으로 읽혀 나레이션을 만들었습니다. 사람이 한 일은 녹화, 컷편집 계획 승인, 장면 확인, 목소리 고르기, 제목과 배경음악과 썸네일, 그리고 공개 여부 판단이었습니다.
