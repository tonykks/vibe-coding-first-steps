git과 GitHub, 사진첩으로 이해하기

바이브코딩을 하다 보면 AI가 자꾸 "commit 할까요?", "GitHub에 push 할까요?"라고 묻습니다. 이 글은 그 말들이 무엇이고 왜 필요한지, 사진첩 하나로 풀어 봅니다.

1 · 한 장의 비유

사진 한 장, 사진첩 하나, 인터넷 사진첩

폴더 하나를 사진첩으로 관리한다고 생각해 보십시오. 고칠 때마다 그 순간의 폴더 전체를 사진으로 찍어 둡니다. 사진 밑에는 무엇을 바꿨는지 한 줄을 적습니다. 이 사진 한 장이 commit이고, 사진첩이 git, 사진첩을 인터넷에 둔 사본이 GitHub입니다.

이름비유하는 일
commit사진 한 장 + 설명 한 줄그 순간 폴더 전체를 기록. b5f3bb0 같은 번호가 붙습니다
git내 PC의 사진첩사진을 순서대로 보관하고, 원하는 번호의 그때 모습으로 되돌립니다
GitHub인터넷에 둔 사진첩 사본다른 PC·다른 사람과 같은 사진첩을 함께 봅니다

사진첩은 저절로 생기지 않습니다. 폴더에서 git init을 한 번 해야 생깁니다. 새 프로젝트를 시작할 때 AI에게 이렇게 한 줄을 덧붙이면 됩니다.

새 프로젝트를 시작할 때 덧붙일 한 줄
이 폴더를 git으로 관리하고, 큰 수정을 마칠 때마다 commit 해 줘.

commit은 사진, git은 내 PC의 사진첩, GitHub은 인터넷에 둔 사진첩입니다.

2 · commit

AI가 왜 자꾸 commit 하자고 할까

바이브코딩에서는 AI가 한 번에 여러 파일을 고칩니다. 잘 되던 기능이 다음 수정에서 깨지는 일도 흔합니다. 이때 사진이 있으면 "어제 오후 사진으로 돌아가 줘" 한마디로 되돌릴 수 있습니다. 사진이 없으면 무엇이 바뀌었는지부터 찾아야 합니다.

  • 되돌릴 자리: 고장 나면 마지막으로 잘 되던 사진으로 돌아갑니다.
  • 바뀐 곳 보기: 앞 사진과 견주면 몇 줄이 어떻게 바뀌었는지 보입니다(git diff).
  • 기록: 사진 설명을 이어 읽으면 이 프로그램이 자라 온 길이 됩니다.

그래서 commit은 "잘 되는 것을 확인한 뒤"에 하는 것이 좋습니다. 고치고, 시험해 보고, 괜찮으면 찍습니다.

commit은 되돌아올 수 있는 자리를 만드는 일입니다.

3 · push와 pull

push와 pull: 두 사진첩 맞추기

사진첩은 두 곳에 있습니다. 내 PC의 사진첩과 GitHub의 사진첩. GitHub에서 저장소(repository)를 만들면 빈 사진첩이 하나 생기고, 그다음부터는 새 사진만 오갑니다.

말방향언제 쓰나
push내 PC → GitHub내가 찍은 새 사진을 올릴 때
pullGitHub → 내 PC다른 PC나 다른 사람이 올린 사진을 내려받을 때
cloneGitHub → 새 PC사진첩을 처음 통째로 복사해 올 때

노트북과 데스크톱을 오가며 일한다면, 시작할 때 pull, 마칠 때 push가 기본 습관입니다. commit만 하고 push하지 않으면 사진은 내 PC에만 있습니다.

push는 올리기, pull은 내려받기. 두 사진첩을 같게 맞추는 일입니다.

4 · 배포

배포: 내 PC 밖으로 내보내기

내 PC에서 만든 웹페이지는 내 PC에서만 열립니다. 주소창에 file:///C:/...로 시작하는 주소는 다른 사람에게 보내도 열리지 않습니다. 다른 사람이 인터넷 주소로 열 수 있게 하는 일이 배포입니다.

GitHub에는 GitHub Pages라는 무료 배포 기능이 있습니다. 저장소에 올린 html 파일을 그대로 웹사이트로 보여 줍니다. 이 강연 사이트도 이렇게 배포했습니다.

  1. 내 PC에서 고치고 commit
  2. GitHub에 push
  3. GitHub Pages가 1~2분 뒤 아이디.github.io/저장소이름 주소에 새 화면을 보여 줌

그래서 GitHub이 중요합니다. 사진첩 보관, 다른 PC와 공유, 웹사이트 공개가 한곳에서 무료로 됩니다. 공개 저장소라면 비용이 없습니다.

배포는 내 PC 안의 결과를 인터넷 주소로 내보내는 일이고, GitHub Pages는 그 가장 쉬운 길입니다.

5 · 다른 배포 사이트

GitHub Pages가 못 하는 일은 다른 곳에서

GitHub Pages는 정적 페이지만 보여 줍니다. 정적 페이지란 누가 열어도 같은 파일(html·css·js)을 그대로 내주는 페이지입니다. 반대로 동적인 일, 곧 서버에서 프로그램이 돌아야 하는 일은 못 합니다.

GitHub Pages로 되는 것GitHub Pages로 안 되는 것
강의 자료·설명 페이지·포트폴리오로그인, 회원 정보 저장
브라우저 안에서만 도는 계산기·타이머·게임데이터베이스에 쓰고 읽기
미리 만들어 둔 표와 그래프비밀 열쇠(API Key)를 숨겨 두고 AI 부르기

이런 일은 Vercel, Netlify, Render, Firebase 같은 배포 사이트가 맡습니다. 이들도 출발점은 GitHub입니다. 저장소를 한 번 연결해 두면, 내가 push할 때마다 그 사이트가 GitHub에서 새 사진을 가져가(pull) 다시 만들고 배포합니다.

  1. 내 PC에서 commit → GitHub에 push
  2. 배포 사이트가 GitHub에서 새 코드를 가져감
  3. 그 사이트의 서버에서 실행·배포

어디에 배포하든 코드의 집은 GitHub입니다. 정적이면 GitHub Pages, 서버가 필요하면 다른 사이트가 GitHub에서 가져갑니다.

6 · React와 Vite

React·Vite로 만든 화면을 GitHub Pages에 올리려면

요즘 AI에게 웹 화면을 만들어 달라고 하면 React와 Vite로 만들어 주는 경우가 많습니다. 이 코드는 사람이 쓰기 편한 모양이라, 브라우저가 바로 읽지 못합니다. 그래서 build를 거쳐야 합니다. build는 그 코드를 브라우저가 읽는 평범한 html·css·js 묶음으로 바꾸는 일입니다. 결과는 dist 폴더에 생기고, 이것은 정적 페이지입니다. 곧 GitHub Pages에 올릴 수 있습니다.

손볼 곳은 세 군데입니다.

어디무엇을왜
vite.config.jsbase: '/저장소이름/' 한 줄 추가사이트 주소가 /저장소이름/ 아래에 있어서, 없으면 화면이 하얗게 나옵니다
.github/workflows/deploy.yml아래 파일 하나 추가push할 때마다 GitHub이 build하고 dist를 배포합니다
GitHub 저장소 Settings → PagesSource를 GitHub Actions로위 파일이 만든 결과를 Pages가 보여 주게 합니다
.github/workflows/deploy.yml
name: Deploy to GitHub Pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: github-pages
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - uses: actions/deploy-pages@v4

직접 쓰지 않아도 됩니다. AI에게 이렇게 말하면 됩니다.

AI에게 맡길 말
이 Vite 프로젝트를 GitHub Pages에 배포하고 싶어.
저장소 이름은 ○○○야. vite.config.js의 base와
GitHub Actions 배포 파일을 만들어 주고,
내가 GitHub 설정에서 바꿀 것을 알려 줘.

화면이 여러 장인 앱이라면 하나 더 살핍니다. 주소를 바꿔 가며 화면을 넘기는 방식(라우터)은 GitHub Pages에서 새로고침하면 "찾을 수 없음"이 뜰 수 있습니다. 이때도 AI에게 "GitHub Pages에서 새로고침해도 되게 해 줘"라고 하면 됩니다.

React·Vite도 build하면 정적 페이지가 되고, 정적 페이지는 GitHub Pages에 올릴 수 있습니다.

7 · Actions

Actions: 정해진 때 저절로 돌아가는 일꾼

GitHub Actions는 GitHub 안의 컴퓨터를 잠깐 빌려 정해진 일을 시키는 기능입니다. 언제, 무엇을 할지는 저장소의 .github/workflows/ 폴더에 있는 설정 파일 하나에 적습니다. 위의 Vite 배포 파일도 Actions였습니다. "push하면 build하고 배포하라"는 일을 시킨 것입니다.

Actions가 실행하는 것은 html 파일이 아니라 프로그램(Python 등)입니다. 그 프로그램이 새 자료를 모아 html을 다시 만들고 commit·push까지 하면, GitHub Pages의 화면이 저절로 새것으로 바뀝니다. 내 PC가 꺼져 있어도 됩니다. 이것이 자동화와 만나는 지점입니다.

언제설정에 적는 말예
push할 때마다on: pushbuild해서 배포, 자동 검사
정해진 시각마다on: schedule매일 아침 자료를 모아 현황 페이지 갱신
내가 버튼을 누를 때on: workflow_dispatch필요할 때만 한 번 실행
매일 오전 9시에 현황 페이지를 새로 만드는 예
name: Daily update
on:
  schedule:
    - cron: '0 0 * * *'   # 세계 표준시 0시 = 한국 오전 9시
  workflow_dispatch:
permissions:
  contents: write
jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: python make_page.py   # 자료를 모아 index.html을 새로 만듦
      - run: |
          git config user.name "github-actions"
          git config user.email "github-actions@users.noreply.github.com"
          git add -A
          git commit -m "자동 갱신" || exit 0
          git push

알아 둘 점이 셋 있습니다.

  • 시각은 세계 표준시(UTC)로 적습니다. 한국 시각에서 9시간을 뺍니다.
  • 정해진 시각보다 몇 분 늦게 돌 수 있습니다. 1초도 어긋나면 안 되는 일에는 맞지 않습니다.
  • 공개 저장소는 무료입니다. 비공개 저장소는 무료 사용 시간이 한 달 2,000분으로 정해져 있습니다. 공개 저장소에 60일 동안 아무 활동이 없으면 시간 예약 실행이 멈춥니다.

Actions는 GitHub 안의 일꾼입니다. 정해진 때 프로그램을 돌리고, 그 결과를 GitHub Pages로 바로 내보낼 수 있습니다.

8 · 덤

git이라는 이름의 장난

2005년, 리눅스 개발자들은 BitKeeper라는 유료 버전 관리 프로그램을 무료로 빌려 쓰고 있었습니다. 그러다 회사와 다툼이 생겨 무료 사용이 끊겼습니다. 리눅스를 만든 리누스 토르발스는 직접 만들기로 하고, 약 열흘 만에 git의 뼈대를 내놓았습니다.

git은 영국 속어로 "고집 세고 못된 녀석"입니다. 리누스는 "나는 자기중심적이라 프로젝트마다 내 이름을 붙인다. 처음엔 Linux, 이번엔 git"이라고 농담했습니다. 첫 설명서에는 기분 좋을 때 읽으면 Global Information Tracker라는 풀이도 적어 두었습니다.

3년 뒤인 2008년, git 사진첩을 인터넷에 맡기고 함께 일하는 사이트 GitHub이 문을 열었습니다. 2018년에 Microsoft가 GitHub을 사들였고, 지금은 Copilot 같은 AI 기능까지 더해졌습니다.

9 · 낱말

낱말 한눈에

낱말한 줄 풀이
repository(저장소)사진첩 하나. 보통 프로젝트 폴더 하나와 같습니다
commit그 순간 폴더 전체를 찍은 사진 + 설명 한 줄
branch사진첩 안의 갈래. 본 줄기(main)를 건드리지 않고 따로 고쳐 보는 자리
merge갈래에서 고친 것을 본 줄기에 합치기
push / pull / clone올리기 / 내려받기 / 처음 통째로 복사해 오기
build사람이 쓰기 편한 코드를 브라우저가 읽는 파일로 바꾸기
배포(deploy)결과를 인터넷 주소로 내보내기
정적 / 동적같은 파일을 그대로 내줌 / 서버에서 프로그램이 돌아 그때그때 만듦
GitHub Pages저장소의 정적 페이지를 무료 웹사이트로 보여 주는 기능
GitHub Actionspush·시각·버튼에 맞춰 GitHub 안의 컴퓨터가 정해진 일을 하는 기능
Pull Request"이렇게 고치자"는 제안. 검토한 뒤 합칩니다

고치고, 시험하고, 찍고(commit), 올리면(push), 세상에 보입니다(배포).
